# 本体论与决策驱动设计：语义骨架如何约束与赋能决策层

> 本文是「AI Agent 架构治理」系列的**决策-本体映射篇**，位于本体认知映射篇（⑫）和本体论基础篇（⑬）之后。
>
> 如果说⑫回答"本体在认知显化管道中扮演什么角色"，本文回答另一个方向的问题：**本体在决策层中扮演什么角色？决策结果如何反馈演化本体？**

**本体在范式中的完整定位**：⑤修订版确认了**领域是第一公民**，认知和决策是服务于领域的路径。本体不是公民——它是领域的形式化表达，是运行在路径上的语义轮子。它不决定路径走向，但每个节点（Parser、Validator、Normalizer、裁决器、执行器、审计器）的运转都依赖它的定义。同时，它也是被决策结果反哺演化的动态系统——轮子会被磨损和更换。本文展开的就是轮子在决策侧的全部细节。

前两篇对本体论的讨论聚焦在认知显化——本体是语义防火墙的目标模式、认知层评估Operational Truth转化为Ground Truth的基准。但本体和决策层之间的关系远不止"目标模式"这么简单。决策层本身就是一个深度依赖本体的系统：它用本体类型裁决、用本体约束验证、用本体事件审计，并且它的输出最终会回过来驱动本体的演化。

---

## 一、总览：本体在决策层中的完整位置

在认知显化与决策驱动设计范式中，本体层与决策层的关系可以用一条双向箭头概括：

```
        本体定义决策的类型空间、约束规则和约束基准
    本体层 ──────────────────────────────────────────→ 决策层
        ←──────────────────────────────────────────
          决策结果驱动本体演化、修正约束、催生新类型
```

⑫篇已经建立了"本体 → 决策"方向的半幅图——本体是语义防火墙的目标模式（Parser验证类型，Validator检查约束，Normalizer完成标准化），防火墙的输出直接进入决策层。本文补上另外半幅图，并深入已有的那半幅。

**核心命题**：本体不仅是决策层的"前置类型声明"，更是决策层运行时治理的语义基础设施。决策四阶段（提案接收 → 裁决 → 执行 → 审计）中，每一个阶段都依赖本体定义的语义结构来完成其确定性职能——而决策的每次执行结果，又成为本体持续演化的输入。

## 二、本体在决策四阶段中的角色

⑤篇定义了决策层的四阶段。结合本体视角，每个阶段的本体参与度可以进一步展开：

### 2.1 提案接收：本体是Parser的匹配目标和Normalizer的实例化模板

这是⑫篇已经充分讨论的阶段。补充两个此前未展开的细节：

**① Parser的类型推测本质上是"本体实例的逆向推理"**。Parser将LLM的自然语言映射到本体类型空间的过程，不同于传统编译器前端将代码映射到AST。传统编译器的类型是确定的（`int x = 1`确定x是整型），而Parser面对的自然语言是模糊的（"改一下auth.ts"可能对应`ModifyFileCommand`或`SearchFileCommand`）。Parser的职责是**在本体类型空间中做一次搜索**——计算自然语言片段与每个Action Type的语义距离，选择最佳匹配。这个过程的可靠性取决于：

- 任务本体定义的Action Type覆盖范围（是否有足够细粒度的动作类型）
- Action Type的参数字段的描述完备性（参数名、类型、默认值、值域是否清晰）
- 每个Action Type的"典型自然语言触发模式"训练数据（一个可选但实践中极有价值的能力）

**② Normalizer输出的"本体实例化"在类型理论中的含义**。Normalizer的输出（`NormalizedAction`）是一个完全满足本体约束的本体实例。这意味着：

```
NormalizedAction = 类型正确（Action Type存在）
                ∧ 参数完整（必填字段非空）
                ∧ 值域合法（每个字段符合ValueType约束）
                ∧ 关系一致（引用的实体ID在对象库中存在或可创建）
                ∧ 默认值已填充（可选字段有合理初始值）
```

当上述五个条件全部满足时，Normalizer输出一个"合法的本体实例"，可以进入裁决器。任何一个条件不满足，Normalizer必须拒绝（throw）或修复（resolve）。当前uncode中Normalizer的透传（`normalized_fields: vec![]`）意味着这五个条件全部跳过——这是🔴级gap。

### 2.2 裁决：本体提供约束公理，裁决器检查本体约束

⑫篇将裁决器映射为任务本体的白名单检查器，但裁决器的本体依赖不止于此。

裁决器需要检查的约束可以分为四个层次，**逐层细化**：

| 约束层次 | 检查内容 | 本体来源 | 示例 |
|:---|:---|:---|:---|
| **Lv1：类型存在** | 动作类型是否在任务本体注册表中 | 任务本体（Action Type集合） | `ModifyFileCommand`是否合法动作？ |
| **Lv2：参数合法** | 参数类型/值域/基数是否符合字段定义 | 应用本体（字段约束） | `operation`的值是否在`["append", "overwrite", "delete"]`中？ |
| **Lv3：权限就绪** | 当前上下文是否有权限执行此动作 | 应用本体（权限约束 + 状态依赖） | 当前pahse是否允许`ModifyFile`？目标文件是否在开放范围内？ |
| **Lv4：副作用可接受** | 动作的执行是否会破坏系统不变量 | 应用本体（关系约束 + 副作用链） | 删除文件是否会导致引用它处出现空引用？ |

在当前的uncode源码中，Lv1-Lv3已有不同程度的实现：
- Lv1存在于`ToolRegistry::active_tool_names()`
- Lv2在Parser/Validator中部分检查
- Lv3在`DecisionPolicy`的4个实现中硬编码
- **Lv4完全空缺**——没有任何检查"一个动作的副作用是否会破坏系统不变量"

**"副作用链"是决策层最值得引入本体建模的概念**。当一个动作被执行时，它的执行可能导致一系列级联变化——修改了一个文件，可能导致依赖它的测试失败，可能导致构建中断。如果任务本体中定义了每个Action Type的`SideEffects`字段（类似Palantir的Action Type定义），裁决器可以在裁决时检查：

```
ModifyFileCommand {
    file: "src/auth/mod.ts",
    operation: "overwrite",
    content: "...",
    side_effects: [
        DependentTest { file: "tests/auth.test.ts", risk: "fail" },
        DependentType { symbol: "AuthModule", risk: "break" },
    ]
}
```

裁决器据此可以：
- 拒绝"高副作用风险 + 低关键优先级"的动作
- 要求"执行前先执行前置动作（先跑测试）"
- 记录副作用到审计轨迹，供事后评估

### 2.3 执行派发：本体Action Type定义执行管线

当裁决器批准了一个动作（`ApprovedAction`），它需要被派发到具体的执行器。执行器的选择、参数绑定、超时策略、重试策略等全部可以从Action Type的元数据中读取。

在当前uncode中，执行派发的管线定义在`ExecutionOrchestrator::dispatch()`中，流程是`prepare_and_validate → hooks → execute → after_hook`。但这个管线对所有Action Type是**统一的**——没有根据Action Type的本体定义来差异化管线行为。

一个本体驱动的执行派发应当支持：

| Action Type属性 | 管线含义 | 示例 |
|:---|:---|:---|
| `timeout_ms` | 执行超时 | `20000` 或 `unlimited` |
| `retry_count` | 失败重试次数 | `0`（无需重试）或 `3`（网络操作） |
| `execution_mode` | 并行/串行 | `serial`（修改文件时）或 `parallel`（读取文件时） |
| `pre_hooks` | 前置校验 | `["check_disk_space", "validate_git_status"]` |
| `post_hooks` | 后置处理 | `["run_formatter", "update_index"]` |
| `log_level` | 审计详细度 | `verbose`（调试）或 `critical`（生产） |

这些字段定义在任务本体的Action Type元数据中，而不是硬编码在管线代码里——裁决器/编排器不再需要理解每个动作的语义，只需要读取本体元数据并执行即可。

### 2.4 审计记录：本体Event Type定义审计结构

审计阶段的输出是`AgentStep`事件，包含action、observation、feedback。从本体视角看，审计事件的本质是**顶层本体的实例化**。

当前uncode的`AgentEvent`定义了32种变体，涵盖了决策轨迹所需的事件类型。但审计事件与Action Type本体定义之间缺少一条关键连接：**审计事件的结构应当自动派生自Action Type的本体定义**，而不是手动定义。

举例：当一个新的Action Type被注册到任务本体时，审计系统应当自动为其生成审计模板：

```
// 任务本体注册一个新Action Type
ActionType::new("WebSearchCommand")
    .with_params(vec!["query: string", "max_results: u32"])
    .with_audit_template(AuditTemplate {
        result_schema: json!({"urls": ["string"], "snippets": ["string"]}),
        summary_field: "query",
    })
// 审计系统自动为WebSearchCommand生成审计记录结构
```

这样做的价值：当系统运行时注册了50个Action Type，审计系统不需要为每个类型单独写代码。审计是自动派生、类型安全的。

## 三、决策反馈到本体：写回的另一半

⑬篇§2.3定义了Operational Truth → Ground Truth的写回机制，描述了"感知 → 决策 → 行动 → 反馈 → 修正"的控制论闭环。但这个描述是从认知层视角出发的——反馈修正的是LLM的下一次上下文。

从决策层视角看，**写回还有另一条路径：决策结果写回本体自身**。这不是修正LLM上下文，而是修正本体定义。这是此前所有文档都未展开的话题。

### 3.1 三类决策驱动的本体演化

决策结果对本体演化的驱动，按影响程度分为三个层次：

| 演化类型 | 触发条件 | 本体影响 | 安全机制 |
|:---|:---|:---|:---|
| **参数调整** | 某字段的`default`值导致多次执行失败 | 更新字段默认值、扩宽值域 | 需经过裁决（类型变更需要系统级审批） |
| **约束修正** | 某约束规则导致合法的业务操作被拒绝 | 修改/移除Validator规则、调整权限阈值 | 约束变更必须记录为本体版本变更 |
| **类型创建** | LLM表达了一种新操作，无对应的Action Type | 在任务本体中创建新Action Type | 新类型需要人工审批或沙箱测试通过后才能激活 |

这三个层次体现了"本体不是静态蓝图"的核心思想——本体在每次决策循环中都可能被决策结果修正。

### 3.2 决策质量驱动约束演化

最直接的写回案例：**裁决器拒绝了某个动作，但后续人工确认该动作实际上应该是合法的**。

```
执行流：
1. LLM提议: ModifyFileCommand { file: "/etc/config.yml", operation: "overwrite" }
2. 裁决器:  拒绝 — PermissionPolicy规则: "禁止修改 /etc 下的配置文件"
3. 人工干预: "这台机器上 /etc/config.yml 是应用配置，允许修改"
4. 系统动作: 修改 PermissionPolicy，将 /etc/config.yml 加入白名单
5. 本体演化: 应用本体中的权限约束被更新（版本 ++）
6. 重放:    ModifyFileCommand 重新裁决 → 通过 ✅
```

在本体化系统中，步骤4-5不是管理员手动改代码，而是通过本体API修改约束公理——变更被版本化记录，可在审计轨迹中回溯。

### 3.3 失败模式驱动约束强化

反面案例：**裁决器批准了某个动作，但该动作的执行导致系统错误**。

```
执行流：
1. LLM提议: ModifyFileCommand { file: "src/main.rs", operation: "delete" }
2. 裁决器:  通过 — 用户有删除权限，文件不在保护名单中
3. 执行器:  执行删除 → CI 构建中断 → 错误上报
4. 分析:    根源是该文件有3个模块引用，删除文件时未检查引用链
5. 本体演化: 为 DeleteFileCommand 添加 side_effects 定义（前置检查引用）
6. 约束强化: 下次 DeleteFile 必须附带 impact_analysis 参数
```

这是**裁决器的Lv4（副作用可接受）循环补全**——初始阶段Lv4是空缺的，失败执行回放后系统发现了需要建模的副作用链，于是约束被补全。

### 3.4 新能力催生新类型

最积极的写回：LLM表达了一种任务本体中不存在的操作，但系统有能力支持。

```
执行流：
1. LLM提议: "我想对 `/tmp/output.json` 做 JSON Schema 校验"
2. Parser:   无法匹配任何已知 Action Type（没有 ValidateJsonSchemaCommand）
3. 系统:     回退为 GenericAction { action: "custom", params: json_raw }
4. 人工/自动: GenericAction 被执行且成功
5. 分析:     这个操作的模式出现 >= 3 次，具备通用化条件
6. 本体演化: 创建 ValidateJsonSchemaCommand { file, schema_ref } 
7. 注册:     新 Action Type 加入任务本体，Parser 可识别
```

新类型创建的本质是**任务本体的增量扩展**——系统运行时发现了一种新的可复用操作模式，将其形式化为一个带命名、参数和约束的Action Type。

## 四、本体约束与决策空间

本体的约束定义决定了决策层的操作空间大小。这部分展开三个此前未深入的话题：**时间约束、资源预算、前置条件链**。

### 4.1 时间约束：本体中的决策时效

在传统DDD中，业务规则的时效性通过领域逻辑隐式表达（"订单提交后24小时内可取消"——写在Service方法里）。在本体化的决策层，时间约束应当是Action Type定义的一部分：

```
ActionType "CancelOrderCommand" {
    params: { order_id: OrderId }
    temporal_constraints: [
        // 只在订单提交后24小时内生效
        WithinTimeWindow {
            start_from: Order.created_at,
            max_delay: Duration::hours(24),
            on_expired: RejectWithReason("订单已超过取消窗口期")
        }
    ]
}
```

裁决器的Lv3（权限就绪）检查中，时间约束是自动执行的——决策层不需要理解"取消订单"的业务，只需要读取本体定义的时间窗口，将其翻译为毫秒级的`current_time < created_at + 24h`检查。

### 4.2 资源预算：本体中的决策配额

LLM的执行不同动作，消耗不同的系统资源。裁决器需要检查的不仅是"这个动作是否合法"，还有"当前是否有配额执行这个动作"。

```
ActionType "RunTestCommand" {
    params: { path: GlobPattern }
    resource_budget {
        cpu_time_ms: 30000,
        memory_mb: 512,
        disk_mb: 200,
        concurrency_limit: 2,  // 最多2个并行测试
    }
}
```

裁决器在Lv3检查时同时执行资源预算校验——如果当前CPU时间已耗尽（LLM在本次turn中已经跑了3次测试），`RunTestCommand`将被拒绝，即使权限和类型都合法。

资源预算的约束定义本身也在应用本体中，可以随会话动态调整（"开启debug模式时，资源预算翻3倍"）。

### 4.3 前置条件链：本体中的执行依赖

某些动作的执行依赖于另一些条件——这不仅仅是"先跑A再跑B"，而是**本体中定义的约束依赖**。

```
ActionType "DeployCommand" {
    params: { target: Environment }
    preconditions: [
        AllTestsPassed { since_commit: git_head },
        NoUncommittedChanges { files: ["src/", "configs/"] },
        ApprovedByReviewer { min_votes: 2 },
    ]
}
```

裁决器在执行前检查这些前置条件——注意，前置条件是本体定义的一部分，不是硬编码在`DeployService::deploy()`方法里的。这意味着决策层不需要理解"部署"是什么，只需要检查`AllTestsPassed`、`NoUncommittedChanges`和`ApprovedByReviewer`三个约束在当前状态下是否满足。

**前置条件链扩展为动态本体概念**后，决策层获得了一种能力：当`DeployCommand`因前置条件不满足被拒绝时，裁决器不仅能回答"不通过"，还能回答"不通过的原因是X未满足，建议先执行Y"。

## 五、本体不确定性与决策确定性

⑬篇强调了本体提供的确定性评价基准，但本体本身也可能存在不确定性。这一问题在之前的讨论中被搁置了。

### 5.1 本体的三类不确定性

| 不确定性类型 | 表现 | 对决策层的影响 |
|:---|:---|:---|
| **类型缺失** | LLM表达了一个无对应Action Type的操作 | Parser无法匹配，候选无法通过防火墙进入决策层 |
| **约束不完整** | Action Type的参数定义缺少某些关键约束 | 裁决器通过了一个实际不该通过的动作（false positive） |
| **约束冲突** | 两个约束规则对同一场景给出矛盾判断 | 裁决器无法确定通过/拒绝，需要冲突解决策略 |

### 5.2 应对策略

**类型缺失**的应对在上文§3.4已讨论：回退为GenericAction + 模式分析 → 新类型创建。

**约束不完整**的应对依赖闭环反馈（§3.3）：执行失败 → 审计分析 → 补全约束。

**约束冲突**则需要裁决器本身内置冲突解决策略：

| 策略 | 行为 | 适用场景 |
|:---|:---|:---|
| **拒绝优先**（Reject-By-Default） | 任何冲突导致拒绝 | 安全敏感操作（文件删除、权限修改） |
| **通过优先**（Allow-By-Default） | 任何冲突导致通过 | 只读操作（搜索、查询、预览） |
| **优先级排序** | 根据约束规则的元优先级裁决 | 明确标注了优先级的约束体系 |
| **人工升级** | 提交给人工裁决 | 高影响度操作，所有自动策略均无法裁决 |

约束冲突的解决策略本身也应当定义在应用本体中，而不是硬编码在裁决器里——不同Action Type可以有不同的冲突解决策略。

### 5.3 本体的版本兼容性与决策回放

这是此前从未讨论的问题。当本体版本化演进后（§3.1），历史决策的审计回放面临兼容性问题：

```
场景：
- 第10轮：裁决器依据本体V1拒绝了 ModifyFileCommand { file: "src/main.rs" }
- 晚上：本体更新为V2 — 添加了新的权限约束规则
- 第二天：审计员回放第10轮的决策链

问题：回放时是用本体V1还是V2的规则？
```

答案取决于回放的目的：

| 回放目标 | 使用哪版本体 | 原因 |
|:---|:---|:---|
| 审计合规性：判断当时的决策是否合法 | 本体V1 | 应使用决策时的本体版本 |
| 审计公平性：判断如果换成现在规则会怎样 | 本体V2 | 评估规则变更的影响 |
| 调试：找出决策当时为什么被拒绝 | 本体V1 + V2 diff | 对照两个版本的差异 |

因此，决策审计轨迹需要**记录本体版本号**——每个`AgentStep`事件中嵌入当时使用的`ontology_version`字段，使得回放引擎可以在本体V1和V2之间切换。

## 六、本体驱动的决策质量评价

⑧篇审计文档中，决策层的评估阶段（H0-H3）已经有了实现——`BasicEvaluator`和`VerifiedEvaluator`。但这些评估器的评价标准来自代码硬编码，不是来自本体定义。

### 6.1 三类本体驱动的评价维度

| 维度 | 本体来源 | 评价问题 |
|:---|:---|:---|
| **合规则** | 应用本体约束公理 | "被批准的动作是否满足当时的所有约束？" |
| **覆盖率** | 任务本体Action Type集合 | "本次turn中LLM使用的动作类型是否覆盖了任务所需的所有操作？" |
| **效率** | Action Type的资源预算 | "执行耗时/资源消耗是否在Action Type定义的合理范围内？" |

这三个维度的评价基准都来自本体定义，评价器只需要读取本体元数据并做数值比较，不需要领域知识。

### 6.2 决策链的因果评价（超越H0-H3）

H0-H3是当前uncode中实现的基本评价层次。引入本体后，可以扩展到更丰富的评价维度：

| 层次 | 名称 | 评价问题 | 本体依赖 |
|:---:|:---|:---|:---|
| H4 | **约束合规性** | 所有被批准的动作是否满足本体约束？被拒绝的动作是否有误拒？ | 应用本体约束公理 |
| H5 | **成本效率** | 每个动作的资源消耗是否在Action Type定义的预算范围内？ | 任务本体资源预算 |
| H6 | **副作用评估** | 动作的副作用是否在预期范围内？是否有未预见的级联影响？ | 任务本体副作用链定义 |

## 七、本体作为多裁决器的协调语言

当系统扩展到多Agent或多裁决器时，本体提供了裁决器间的语义协调基板。

### 7.1 问题：两个裁决器如何对齐？

```
裁决器A（核心工具裁决器）：批准 ModifyFileCommand { file: "src/main.rs" }
裁决器B（安全审计裁决器）：需要知道A批准了什么，以便做安全审计

没有本体：
  - A的输出是 Rust struct ModifyFileCommand
  - B需要解析A的内部类型才能理解
  - A和B负责同一动作的不同约束（工具合法性 vs 安全合规性）
  - 扩展第三个裁决器（如成本裁决器）时，需要重新理解ModifyFileCommand

有本体：
  - A和B共享同一个任务本体定义 ModifyFileCommand
  - A的输出是本体实例（JSON形式），B可以直接消费
  - 新的裁决器只需要注册到本体的事件总线，自动收到结构化的裁决事件
```

### 7.2 裁决器的链式编排

本体Action Type的定义可以包含"这个动作需要哪个裁决器序列来审批"：

```
ActionType "DeleteFileCommand" {
    adjudicator_chain: [
        "PermissionPolicyAdjudicator",    // Lv2: 权限检查
        "ImpactAnalysisAdjudicator",      // Lv4: 副作用检查
        "UserConfirmationAdjudicator",    // Lv4+: 人工确认
    ],
}
```

裁决器链不是硬编码的，而是由任务本体的Action Type元数据驱动。添加一个新的裁决器不需要修改现有裁决逻辑——只需要在任务本体中声明，"从此以后，所有`DeleteFileCommand`需要经过`ImpactAnalysisAdjudicator`审查"。

## 八、实践检查：uncode 当前状态

基于⑧篇审计文档的缺口，结合本文的分析，可以更精确地定位uncode的决策-本体差距：

| 本文概念 | uncode 现有实现 | 状态 |
|:---|:---|:---:|
| Parser的类型推测引擎 | `DefaultParser::parse()` — 基于ToolRegistry匹配 | ✅ 基础 |
| Normalizer的本体实例化 | `normalized_fields: vec![]` — 透传 | 🔴 |
| 裁决器Lv4副作用检查 | 不存在 | 🔴 |
| Action Type元数据驱动的执行管线 | `ExecutionOrchestrator` 统一管线 | 🟢 可扩展 |
| 审计事件派生自Action Type定义 | 手动定义32变体 | 🟡 无自动派生 |
| 决策驱动的本体演化 | 不存在 | 🔴 |
| 时间约束 / 资源预算 / 前置条件 | 不在Action Type定义中 | 🔴 |
| 本体版本化与决策回放兼容 | 不存在 | 🟡 |
| 本体驱动的H4-H6评价 | 不存在 | 🟡 |
| 多裁决器链式编排 | 单裁决器 | 🟢 架构支持扩展 |

其中最值得优先投入的点（本文新发现，未出现在⑧篇审计中）：

1. **Lv4副作用检查**：没有检查动作的级联影响。这是"决策质量"提升空间最大的单项改进。
2. **Action Type元数据**：将Action Type定义从工具模块的分散代码中提取为集中声明式注册——每一类动作都附带timeout、retry_args、adjudication_chain等元数据。
3. **本体版本号嵌入决策轨迹**：在`AgentStep`或`DecisionRecord`中添加`ontology_version`字段，为未来的历史回放兼容做好准备。

## 九、总结

| 问题 | 回答 |
|:---|:---|
| 本体在决策四阶段中的角色？ | 提案接收：Parser匹配目标 + Normalizer实例化模板。裁决：Lv1-Lv4约束公理检查。执行：Action Type元数据驱动管线差异化。审计：事件结构派生自Action Type定义。 |
| 决策如何反馈到本体？ | 三类演化：参数调整（约束微调）、约束修正（规则补全或放宽）、类型创建（新Action Type注册）。 |
| 本体不确定性如何影响决策确定性？ | 类型缺失→GenericFallback。约束不完整→闭环补全。约束冲突→策略化解决（拒绝/通过/优先级/升级）。本体版本化→审计回放时需选择对应版本。 |
| 本体对决策质量评价的价值？ | 提供合规则、覆盖率、效率三个维度的可度量基准；扩展H4-H6层次（约束合规性、成本效率、副作用评估）。 |
| 本体在多裁决器中扮演什么角色？ | 语义协调基板——不同裁决器通过共享本体实例理解同一个动作；裁决器链由Action Type元数据驱动。 |

**一句话总结**：本体是决策层的"语义操作系统"——它定义了决策空间的大小（约束）、决策过程的形状（类型）、决策质量的基准（评价）、决策结果的归宿（审计），并在每次决策循环中被决策结果反哺演化。
