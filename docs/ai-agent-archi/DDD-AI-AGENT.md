# 当确定性遇到概率性：DDD 在 AI Agent 系统中的适应与重生

“DDD 不适合 AI Agent 开发”——这个判断最近越来越常见。它并不完全错，但也不完整。更准确地说，经典 DDD 之所以在 AI Agent 场景里显得吃力，不是因为它没用了，而是因为它默认的世界是确定性的，而 Agent 世界是概率性的。 [martinfowler](https://martinfowler.com/bliki/DomainDrivenDesign.html)

如果把这个问题说透，会发现真正需要改变的，不是 DDD 的核心思想，而是我们对 DDD 的使用方式。  
在传统业务系统里，DDD 负责把复杂业务拆成边界清晰、规则明确的模型；在 AI Agent 系统里，它更像一套**边界治理方法**，帮助我们把确定性和概率性分开，把可验证的部分和不可预测的部分隔离开来。 [martinfowler](https://www.martinfowler.com/bliki/BoundedContext.html)

## 为什么这个问题值得讨论

AI Agent 和传统业务系统最大的差异，不在于“有没有智能”，而在于**行为是否可预测**。  
在电商、银行、ERP 这类系统里，通常可以假设：同样的输入，在同样的上下文下，应该得到稳定的输出。DDD 的很多战术模式，比如实体、值对象、聚合、领域服务，都是建立在这个前提上的。 [martinfowler](https://martinfowler.com/bliki/DomainDrivenDesign.html)

但 AI Agent 不一样。它往往由 LLM 驱动，带着上下文、记忆、工具调用和外部反馈一起工作。一次任务可能横跨多轮推理、多次工具调用、人工确认、失败重试和路径修正，整个过程不再是一个短事务，而是一个长流程。 [axoniq](https://www.axoniq.io/blog/agentic-ai-architecture-event-store-databases-for-glass-box-ai-systems)

这就带来一个很现实的问题：  
**如果系统的核心决策本身是概率性的，DDD 还应该怎么用？**

我的答案是：  
DDD 不是不适合 AI Agent，而是必须从“业务规则建模”升级为“认知边界设计”。

## 经典 DDD 为什么会吃力

### 确定性和概率性不在一个世界

经典 DDD 的底层假设很清楚：领域模型要能表达规则，规则应该可解释、可测试、可重复。  
这也是为什么我们会认真设计聚合根、领域服务和规约模式，因为它们本质上都在追求稳定的可推理行为。 [martinfowler](https://martinfowler.com/bliki/DomainDrivenDesign.html)

而 LLM 驱动的 Agent 不遵守这种稳定性。  
同样的任务描述，不同时间、不同上下文、不同提示词细节，可能得到不同的计划、不同的工具选择，甚至不同的执行路径。  
这意味着系统不再只是“执行业务规则”，而是在“生成下一步动作”。

换句话说，传统 DDD 擅长的是“规则驱动”，Agent 更像是“生成驱动”。

### 聚合边界和任务边界不一致

DDD 中的聚合，通常是围绕一致性边界来设计的。  
它适合管理局部状态，适合短事务，适合在一个有限范围内完成状态转换。 [martinfowler](https://www.martinfowler.com/bliki/BoundedContext.html)

但 Agent 的任务边界远比这长。  
比如“给登录系统加双因素认证”这样一个任务，可能包含：

- 理解需求。
- 检索代码结构。
- 生成实现方案。
- 修改多个文件。
- 运行测试。
- 分析失败。
- 回滚重试。
- 再次审查。

这个过程可能持续几分钟甚至更久。  
如果硬把整个任务塞进一个聚合里，聚合会迅速膨胀；如果把它拆得太碎，又会丢失上下文连续性。

所以，Agent 系统里的边界不能再只按“事务一致性”来划分，还必须按“决策合法性”和“上下文连续性”来划分。

### 显式规则和涌现行为之间有鸿沟

DDD 的一个核心价值，是把隐性的业务知识变成显性的代码模型。  
但 AI Agent 的很多行为并不是程序员提前写好的 if-else，而是在上下文、示例、模型参数和推理过程中涌现出来的。 [martinfowler](https://martinfowler.com/bliki/DomainDrivenDesign.html)

这会直接带来两个问题：

- 业务逻辑有一部分跑进了提示词里。
- 关键决策不再完全可见，也不再天然可审查。

从工程实践看，这不是“模型更强了”的简单问题，而是软件的可治理性发生了变化。  
你依然需要模型，但模型的角色从“表达一切规则”，变成了“约束一部分行为”。

### 无状态服务不再够用

传统 DDD 更偏爱无状态服务。  
无状态意味着更容易测试、更容易复用，也更符合服务化设计的思路。 [martinfowler](https://martinfowler.com/bliki/DomainDrivenDesign.html)

但 Agent 的服务调用往往天然依赖状态：

- 最近的会话历史。
- 当前工作区内容。
- 工具返回结果。
- 外部环境变化。
- 用户临时反馈。

这使得“服务无状态”这条原则不能简单照搬。  
更合理的做法不是隐藏状态，而是把状态显式参数化，让服务仍然保持纯函数式的可测试风格，但上下文依赖被明确暴露出来。

## DDD 该怎么适配

### 限界上下文重新变得重要

如果说传统 DDD 里限界上下文是“组织大型领域模型的方式”，那么在 AI Agent 场景里，它更像是一道**认知隔离墙**。 [martinfowler](https://www.martinfowler.com/bliki/BoundedContext.html)

因为 Agent 系统里通常同时存在三种不同性质的区域：

- 确定性区域：状态机、权限、资源控制、工具执行。
- 概率性区域：LLM 调用、计划生成、解释与改写。
- 混合区域：编排、反馈回路、人工确认。

这三类区域不应该混在一个模型里。  
一个好的架构，应该让 LLM 留在概率性上下文中，让核心业务约束留在确定性上下文中，中间通过防腐层连接。

这一步很关键。  
它不是简单的模块拆分，而是把不同类型的计算放进不同的治理机制里。

### 聚合要从事务边界变成决策边界

在 AI Agent 系统里，聚合不一定要承载完整任务生命周期。  
它更适合做“决策裁决者”：判断某个动作是否允许、某个状态是否合法、某个提案是否能进入核心域。

比如：

```ts
class Agent {
  decide(action: ProposedAction): ApprovedAction {
    if (!this.policy.allows(action)) {
      throw new PolicyViolation();
    }
    return this.guardrails.normalize(action);
  }
}
```

这个思路很重要。  
LLM 可以负责提出方案，但最终进入系统状态的，必须是经过裁决和验证的结果。  
这样做的本质，是把 DDD 从“状态建模”推进到“行为约束建模”。

### 防腐层要升级成语义防火墙

传统防腐层主要解决系统之间的模型转换问题。  
但在 Agent 系统里，它还必须承担更多职责：

- 把自然语言输出结构化。
- 过滤不合法的动作。
- 统一命名和语义。
- 处理置信度和歧义。

也就是说，它不只是做 translation，更是在做 **semantic firewall**。  
LLM 输出不能直接进入领域层，必须先经过解析、验证和规范化，才算是可执行命令。

一个很实用的原则是：  
**领域层永远不接触自然语言，只接触结构化语义。**

### 事件流应该成为一等公民

在传统 DDD 中，领域事件的作用主要是通知。  
在 AI Agent 中，事件链本身就是产品的一部分。 [akka](https://akka.io/blog/event-sourcing-the-backbone-of-agentic-ai)

为什么？因为 Agent 的核心价值之一，就是它做了什么、为什么这么做、在哪一步出了问题、后来怎么修正。  
如果没有事件流，你就很难调试 Agent，很难回放任务，很难分析失败模式，也很难做离线优化。

所以，Agent 里的事件不只是“发生了什么”，而是：

- Agent 看到了什么。
- 它做了什么决策。
- 它调用了什么工具。
- 工具返回了什么。
- 它如何修正路径。

这套事件流天然适合做可观测性、审计、回放和评估。  
而事件溯源一类的架构模式，也正越来越被视为 agentic AI 的基础设施。 [axoniq](https://www.axoniq.io/blog/agentic-ai-architecture-event-store-databases-for-glass-box-ai-systems)

### 服务状态要显式外化

面对 Agent 的上下文依赖，与其说服务“有状态”，不如说状态应该被**显式输入化**。  
也就是说，服务本身仍然尽量保持无副作用，只是它做决策时依赖的状态必须以参数方式传入。

例如：

```ts
async function determineNextAction(
  agentState,
  eventHistory,
  workspaceDelta,
  toolRegistry
) {
  // 基于显式上下文做决策
}
```

这样做的好处是保留了可测试性，也保留了可替换性。  
你不是把状态藏起来，而是把状态变成一等输入。

## 一个值得参考的实践样本

如果看开源项目的实践，像 `pi` 这类 Agent 项目就比较接近这种思路：把概率性能力和确定性核心分开放在不同模块里，让 LLM 调用停留在独立上下文中，而把 Agent 状态机、工具调度和执行逻辑放在更确定的核心域里。 [2025.dddeurope](https://2025.dddeurope.com/program/event-sourcing-the-backbone-of-agentic-ai/)

这种拆法的价值，不在于它“用了 DDD 的术语”，而在于它体现了一个非常现实的工程判断：  
**不要让概率性逻辑污染核心状态。**

从这个角度看，几条设计原则会变得很清楚：

- 隔离概率性：LLM 放在独立上下文。
- 事件为纲：完整记录行动轨迹。
- 建立验证层：LLM 输出必须经过校验。
- 保持可观测：完整回放和审计能力是刚需。
- 模块化作为治理手段：边界就是管理复杂度的工具。

这些原则并不花哨，但很实用。  
它们说明，DDD 在 Agent 场景里不是失效了，而是被迫回到自己最擅长的地方：**通过边界治理复杂性**。 [martinfowler](https://www.martinfowler.com/bliki/BoundedContext.html)

## 我们真正需要的是什么

如果再往前走一步，我会把这种设计理解为一种更广义的“适应性 DDD”或者“认知驱动设计”。  
它不要求系统行为完全可预测，但要求关键行为可验证；它不要求所有逻辑都写死在代码里，但要求所有关键决策都能被追踪和解释。

这其实比传统 DDD 的要求更现实，也更符合 AI Agent 的本质。  
因为 Agent 不是单纯的业务执行器，而是一个会观察、推理、行动、修正的认知系统。

在这种系统里，DDD 的角色变了：

- 不再只是管理业务规则。
- 而是管理认知边界。
- 管理概率性和确定性的接口。
- 管理可见与不可见之间的转换。

## 最后怎么落地

如果你现在正在做 AI Agent 系统，我建议从这三步开始：

### 1. 先画边界，不要先堆模型

先区分哪些部分是确定性的，哪些部分是概率性的。  
把 LLM、计划生成、自然语言解释单独放到一个上下文里，把状态机、权限、执行和审计放到另一个上下文里。 [martinfowler](https://www.martinfowler.com/bliki/BoundedContext.html)

### 2. 先设计事件，再设计状态

不要一上来就问“当前状态怎么存”。  
先问：系统里最重要的事件是什么？哪些事件必须能回放？哪些事件必须能审计？  
因为对 Agent 来说，历史往往比当前状态更重要。 [akka](https://akka.io/blog/event-sourcing-the-backbone-of-agentic-ai)

### 3. 先做验证层，再做智能层

LLM 的输出一定要先经过验证、结构化和规范化，再进入核心域。  
不要让自然语言直接变成领域动作。  
这是控制风险最直接、也最有效的方法。

## 结语

所以，如果把这件事说得更直白一点：  
DDD 不是死了，它只是换了一个更难的战场。

在传统业务系统里，DDD 帮我们管理规则。  
在 AI Agent 系统里，DDD 要帮我们管理的是**可能性**。  
LLM 负责生成可能性，DDD 负责约束可能性；LLM 负责探索路径，DDD 负责守住边界。

这也是我对这个问题最简洁的判断：

**不是 DDD 不适合 AI Agent，而是 AI Agent 迫使 DDD 从“确定性建模”走向“概率性边界设计”。**
