# 认知显化与本体映射：认知到决策的语义基础设施

> 本文是「AI Agent 架构治理」系列的**语义桥梁篇**，连接收口篇（⑤范式定义）与本体论基础篇（⑬知识体系）。
>
> 回答这样一个问题：**认知显化管道中的"显化为谁"——语义防火墙输出的结构化结构，其类型体系来自哪里？**
>
> 前置阅读：`ontology-foundations.md`（⑬）提供了本体的完整知识体系，本文是其范式侧的映射对位。

收口篇（`cognition-decision-driven-design.md`）定义了认知显化与决策驱动设计的完整范式，核心链条是：

```
模糊 → Parser → Validator → Normalizer → 显式 → 决策层
```

这个链条回答了**"怎么转"**，但没有追问：**"转成什么"？** Normalizer 输出的 `ModifyFileCommand`，其类型结构是谁定义的？`ParsedAction` 的字段约束由谁规定？

答案在语义防火墙的背面——**本体**。

---

## 一、核心论点

**本体是认知显化的"目标模式"——说明"转成什么"；语义防火墙是运行时的翻译管道——执行"怎么转"。两者合在一起，才构成完整的"模糊→结构"语义闭环。**

```
语义防火墙                            本体层
┌──────────────────┐                ┌──────────────────┐
│  Parser           │                │  顶层本体         │
│  (自然语言→草稿)   │                │  (AgentStep, Event)│
│       ↓           │    引用本体     │                  │
│  Validator        │ ←──────────── │  领域本体         │
│  (约束检查)       │    类型系统     │  (File, Function) │
│       ↓           │                │                  │
│  Normalizer       │                │  任务本体         │
│  (归一化映射)      │                │  (Modify, Search) │
│       ↓           │                │                  │
│  ApprovedAction   │                │  应用本体         │
│  (进入决策层)      │                │  (ModifyFileCmd)  │
└──────────────────┘                └──────────────────┘
```

**本文的核心任务**：将本体论基础（⑬）的九个主题映射到认知显化范式中。对每个本体概念，本文不重复基础定义，而是回答"它在范式中对应什么、承担什么角色、受什么约束"。

---

## 二、本体是什么——信息系统的语义骨架

引自业界通识定义：

> **本体是对共享概念的形式化、显式的规范。**——Gruber, 1993

### 2.1 本体核心三要素

对 Agent 系统而言，本体核心表达三件事：

| 要素 | 定义 | 在 Agent 中的例子 |
|:---|:---|:---|
| **类型（类）** | 事物是什么 | `File`, `Function`, `ModifyFileCommand` |
| **属性（槽位）** | 事物的特征 | `file.path: String`, `operation: Enum` |
| **约束（公理）** | 事物间的关系规则 | `operation` 必须是 `append`/`overwrite`/`delete` 之一 |

### 2.2 本体 vs 相邻概念

在认知显化管道中，这三个概念各自承担不同的语义职责：

| 维度 | 数据模型 | 本体 | 知识图谱 |
|:---|:---|:---|:---|
| **在范式中的位置** | 决策层的存储格式 | 语义防火墙的引用标准 | 决策审计的关联数据 |
| **抽象层次** | 物理/逻辑 | 概念/语义 | 实例/关联 |
| **表达能力** | 结构约束（类型、长度） | 逻辑公理（继承、约束、关系） | 事实三元组 |
| **变动成本** | 高（需迁移数据） | 中（版本化迭代） | 低（增量添加） |
| **对应物 in uncode** | `ApprovedAction` 的序列化格式 | `ParsedAction` → `NormalizedAction` 的类型定义 | `AgentEvent` 链的实体关联 |

本体独立于实现语言——它是**"数据的形状协议"**，不关心用 Rust struct 还是 JSON Schema 表达。

## 三、本体的哲学基础在管道中的映射：Ground Truth → Operational Truth

⑬ §2 阐述了本体的两种真相观。在认知显化管道中，这套哲学框架有直接的工程对应：

### 3.1 管道哲学映射

| 管道阶段 | 哲学对应 | 本质 | 验证方式 |
|:---|:---|:---|:---|
| **LLM 生成候选** | Operational Truth | 任务上下文中"暂时为真"的假设 | 不验证——认知层只负责生成 |
| **Parser** | Operational Truth 结构化的开始 | 自然语言 → 候选结构，语义第一次显化 | 类型匹配——能否解析为已知类型 |
| **Validator** | Ground Truth 检查的入口 | 系统层不信任 LLM 的输出，必须验证合法性 | 本体约束检查——是否在白名单内、值域是否正确 |
| **Normalizer** | 从 Operational 到 Ground 的跃迁 | 将仍带 LLM 噪音的候选映射为标准化本体实例 | 映射完整性——所有必需属性和关系是否到位 |
| **决策层裁决** | Ground Truth 的锁定的体现 | 裁决器基于本体实例执行权限和安全策略 | 裁决通过/拒绝 |
| **执行 + 审计** | 写回机制 | 执行结果写回事件流，修正认知层下一轮上下文 | 事件完整性——决策轨迹不可变 |

### 3.2 写回机制的工程对应

Operational Truth 的写回机制在认知显化管道中有两层实现：

| 写回级别 | 认知显化中的对应物 | 作用 |
|:---|:---|:---|
| **L1：事件流回写** | `ExecutionResult → AgentStep → 事件链 → 认知层上下文重建` | 修正 LLM 下一轮推理的上下文 |
| **L2：训练数据回写** | `决策轨迹 → 评估 → 反馈 → 模型进化` | 修正模型自身的行为 |

### 3.3 范式意义

> **语义防火墙本质上是一个 Operational Truth → Ground Truth 的工业化转换流水线。**

认知层的 LLM 生成候选（Operational Truth），防火墙逐步将候选转化到系统可信任的结构（Ground Truth），决策层基于 Ground Truth 做不可回退的操作。这正是收口篇所述"可以犯错"与"不能犯错"的分界线的哲学对应。

### 3.4 本体层对概率性的评价含义

本体层的引入带来了一个关键的范式级洞察：**本体不是让 LLM 的概率性输出变确定，而是给出了"概率性输出 → 确定性规约"的转化评价基准。**

这个洞察可以从两个维度理解：

**第一，本体定义了"不能犯错"维度的具体评价项。** 没有本体时，"输出是否合法"是一个模糊问题，通常依赖 LLM-as-judge 或运行时崩溃来发现。有本体后，防火墙的每一步评价都是确定性的：

| 维度 | 无本体时的评价 | 有本体时的评价 |
|:---|:---|:---|
| 输出是否可解析 | 正则硬匹配或 LLM 重试 | Parser 类型匹配（确定性的通过/拒绝） |
| 动作是否被允许 | 提示词约束 + 人工审查 | Validator 白名单检查（确定） |
| 参数是否合法 | 运行时崩溃才知道 | Normalizer 提前验证（确定） |

**第二，本体把 LLM 的犯错空间从"什么都能错"约束到"只能在策略层面犯错"。** 类型不对、动作违法、参数越界——这些错误在到达执行器之前就被防火墙拦截了。LLM 真正的"自由度"被限制在策略选择层面（选哪个工具、用哪个参数值、按什么顺序执行），而这正是认知层应该负责的领域。

> **本体的工程意义：不是消除不确定性，而是划定不确定性的合法边界。**

## 四、本体四层在认知显化链中的对应位置

### 4.1 顶层本体 → 事件系统

| 本体 | 认知显化链中的位置 | 作用 |
|:---|:---|:---|
| **顶层本体** | 治理层（事件系统） | 定义跨领域的通用基础概念：时间、空间、对象、事件、过程 |

在 uncode 中，顶层本体表现为 `AgentEvent` 枚举的 32 个变体——每个变体都是一个"通用事件类型"的定义：

- `StepEvent` → "事件"类的实例
- `StateChange` → "状态转换"类的实例
- `ErrorEvent` → "异常"类的实例

顶层本体贵在**跨领域共识**。无论上层认知层换了什么模型、下层执行了什么工具，`AgentEvent` 的结构不变——这是整个系统的语义最低公约数。这与⑬ §3.1 中 BFO/SUMO 等顶层本体的定位一致：保障不同子系统间的最底层交互。

### 4.2 领域本体 → 工具系统的实体类型（对应 Palantir Semantic Layer）

| 本体 | 认知显化链中的位置 | 范式对应 | Palantir 对应 |
|:---|:---|:---|:---|
| **领域本体** | 认知层 → 防火墙（实体类型） | 定义特定领域核心概念及其关系 | **Semantic Layer**——"世界是什么"：对象类型、属性、链接类型 |

工具系统的类型定义本质上是领域本体的工程化表达：

```
领域本体概念         Rust 类型                    Palantir 对应
──────────────────────────────────────────────────────────────────
"文件"     →    File { path, content, language }   ObjectType: File
"函数"     →    Function { name, signature, body }  ObjectType: Function
"代码范围"  →    CodeRange { ... }                   Property: CodeRange
"补丁"     →    Patch { original, modified }        ObjectType: Patch
```

这些类型不因 LLM 输出的表述方式而改变。这正是本体"共享概念的形式化规范"的含义。在 Palantir 架构中，这一类定义由 **OMS（Ontology Metadata Service）** 管理，作为元数据注册表供整个平台引用。

### 4.3 任务本体 → 动作类型集（对应 Palantir Kinetic Layer）

| 本体 | 认知显化链中的位置 | 范式对应 | Palantir 对应 |
|:---|:---|:---|:---|
| **任务本体** | 防火墙 → 裁决器 | 定义系统可理解的动作类型——"系统能做什么" | **Kinetic Layer**——"世界如何变化"：Action Type、对象函数、数据管道 |

裁决器能理解哪些动作——这个有限集合就是任务本体：

```
任务本体概念        裁决器可接受的动作            Palantir Action Type
─────────────────────────────────────────────────────────────────────
"修改文件"  →    ModifyFileCommand                Action: ModifyFile
"搜索代码"  →    SearchCodeCommand                Action: SearchCode
"创建文件"  →    CreateFileCommand                Action: CreateFile
"执行命令"  →    ExecuteCommand                   Action: ExecuteCommand
```

关键约束：**任务本体是裁决器的白名单**。在 Palantir 术语中，这就是 Actions Service 的职责——`InputParams → Validation → ObjectEdits → SideEffects`。本体的边界就是护栏的边界。

### 4.4 应用本体 → 语义防火墙输出层（对应 Palantir Dynamic Layer）

| 本体 | 认知显化链中的位置 | 范式对应 | Palantir 对应 |
|:---|:---|:---|:---|
| **应用本体** | Normalizer → 决策层 | 最具体的语义模型，结合领域概念与任务约束 | **Dynamic Layer**——"世界如何决策"：规则、AI、权限、模拟 |

Normalizer 的本质工作：**将经过验证的候选（仍可能带 LLM 的表述噪音）映射为应用本体的标准实例。**

```
LLM 说："搜索所有包含 TODO 的测试文件"
Parser  →  { action: "search", query: "TODO", files: "test_*" }
Validator →  { approved: true, scope: "test/" }
Normalizer →  SearchCodeCommand { pattern: "TODO", path_pattern: "test/*", case_sensitive: false }
```

Normalizer 做的三件事，每一步都依赖于应用本体：

1. **字段值归一化**：`"test_*"` 根据本体约束修正为 `"test/*"`
2. **默认值填充**：`case_sensitive: false` 来自本体的属性默认值定义
3. **关系验证**：确认 `pattern` 和 `path_pattern` 的类型匹配

### 4.5 双重视角：本体四层分类 vs Palantir 三层架构

将两个分类体系并排放置，可以看到它们从不同粒度描述了同一语义基础设施：

```
本体四层分类（抽象粒度）     Palantir 三层架构（运行时组织）        认知显化范式
──────────────────────────  ──────────────────────────────        ──────────────
顶层本体（跨领域通用概念）                                        事件系统 / 治理层
                              Dynamic Layer（世界如何决策）
领域本体（行业专属概念）       Kinetic Layer（世界如何变化）       认知层 + 防火墙
任务本体（动作/过程概念）      Semantic Layer（世界是什么）        防火墙 + 裁决器
应用本体（系统级具体实例）                                        防火墙输出 → 决策层
```

关键差异：

| 维度 | 本体四层分类 | Palantir 三层架构 |
|:---|:---|:---|
| **切分依据** | 抽象程度（通用 → 具体） | 运行时职责（定义 → 变化 → 决策） |
| **适用场景** | 知识工程、标准制定 | 平台工程、运行时治理 |
| **动词位置** | 任务本体（独立的层） | Kinetic Layer（中间层） |
| **对范式的启发** | 告诉认知显化管道"有哪些类型层次" | 告诉认知显化管道"运行时各层的职责边界" |

## 五、认知显化管道作为运行时本体引擎

### 5.1 认知显化阶段与本体功能的完整映射

| 认知显化阶段 | 本体功能 | 输入 | 输出 | 失败模式 |
|:---|:---|:---|:---|:---|
| **Parser** | 本体实例推测 | 自然语言 | 未经验证的候选结构 | 类型不匹配——无法解析为任何已知本体类型 |
| **Validator** | 本体约束检查 | 候选结构 | 合法性判定 + 违规报告 | 违反约束——动作不被允许或参数非法 |
| **Normalizer** | 本体实例标准化 | 合法候选 | 标准化本体实例 | 映射不完整——缺少必需属性或关系 |
| **执行器** | 本体实例消费 | 标准化实例 | 执行结果 + 新事件 | 执行失败——本体实例与实际世界状态不匹配 |

这个管道本质上是一个**运行时本体引擎**——它不接受任意 JSON，只接受符合本体定义的结构实例；它不信任 LLM 的格式承诺，通过三层逐步验证将自然语言还原为本体实例。

这也是本体层对 LLM 概率性输出的核心评价含义：**本体不是让概率性变确定，而是给出了"概率性输出 → 确定性规约"的转化评价基准。** 上表中每一行的失败模式都是确定性的通过/拒绝——Parser 能否解析为已知类型、Validator 是否检查通过、Normalizer 是否映射完整，不依赖另一个 LLM 做评判。本体把 LLM 的犯错空间从"什么都能错"约束到"只能在策略层面犯错"。

### 5.2 与传统本体引擎的对比

| 维度 | 传统本体引擎（Protégé + OWL） | 认知显化管道 |
|:---|:---|:---|
| 使用时机 | 设计时/编译时 | 运行时/推理时 |
| 输入 | 人工编辑的本体文件 (OWL/RDF) | LLM 自然语言输出 |
| 推理方式 | 描述逻辑推理 | Parsing → Validation → Normalization |
| 输出 | 一致性报告/代码 | 可执行的结构化命令 |
| 受众 | 知识工程师 | Agent 决策层 |

### 5.3 与 Palantir 语义编译栈的对照

⑬ §6.3 描述了 Palantir 的语义编译栈。其三层结构与认知显化管道有直接的对应关系：

| Palantir 语义编译栈 | 对应认知显化阶段 | 共同本质 |
|:---|:---|:---|
| **语义抽象层**：解析本体意图和对象类型 | **Parser**：自然语言 → 候选结构 | 从自然表述中提取语义骨架 |
| **逻辑变换层**：优化逻辑 DAG，生成依赖图 | **Validator + Normalizer**：约束检查 + 归一化 | 消除歧义、验证合法性、优化结构 |
| **执行绑定层**：注入策略，绑定到具体代码 | **决策层执行**：派发 + 执行 + 审计 | 将语义指令转化为具体操作 |

差异在于：

- **Palantir 编译栈**的输入是设计时编写的形式化本体 + 代码函数，输出是可执行的**逻辑计划**（语义字节码）
- **认知显化管道**的输入是 LLM 自然语言，输出是可执行的**结构化命令**（本体实例）

两者面对的根本问题不同——前者是"如何编译形式化知识为可执行计划"，后者是"如何将 LLM 的非确定性输出转化为确定性命令"。

## 六、动态本体：当动词成为第一公民

### 6.1 从静态到动态

⑬ §6.1 对比了静态本体与动态本体的核心差异：

| 对比维度 | 静态本体 | 动态本体 |
|:---|:---|:---|
| **定义时机** | 设计时 | 运行时 |
| **变更方式** | 重新部署 | 版本化迭代 |
| **执行为** | 文档/规范 | 运行时引擎 |
| **与数据源的关系** | 映射 | 映射 + 回写 |
| **控制论闭环** | 无 | 触发 → 执行 → 反馈 → 调节 |

### 6.2 动词独立化：与"决策第一公民"的共鸣

传统本体偏静态：

```
本体（传统）= 名词（实体 + 属性 + 关系），动词是附属于关系的"角色名"
```

决策驱动范式要求动词拥有独立地位：

```
本体（动态）= 名词（实体） + 动词（动作/决策） + 数据源绑定（上下文）
```

为什么动词必须独立？因为**决策层裁决的是动作，不是实体。**

| 传统本体 | 动态本体（决策驱动） |
|:---|:---|
| "员工工作于公司"——"工作"是关系属性 | `WorkCommand { employee, company, start_date }`——"工作"是可执行的动作类型 |
| 动词隐含在对象属性中 | 动词显式化为第一公民类型 |
| 推理方向：实体关系的分类 | 推理方向：动作的合法性、权限、副作用 |
| 实例化结果：三元组 (Subject-Predicate-Object) | 实例化结果：事件 (Action + Actor + Context + Result) |

这与范式收口篇的判断完全一致：**LLM 可以换，决策的正确性必须保证。**

动态本体的工程意义：**当动词是独立类型时，裁决器可以在不依赖 LLM 的情况下验证动作合法性。** 裁决不需要"理解"自然语言，只需要检查 `ModifyFileCommand` 的实例是否满足权限规则和参数约束——而这一切在 Normalizer 完成后即可完成。

### 6.3 控制论闭环：从 Palantir 到认知显化管道

⑬ §6.4 描述了 Palantir 动态本体的控制论闭环。这个闭环与认知显化管道的事件循环高度同构：

| Palantir 控制论闭环 | 认知显化管道事件循环 |
|:---|:---|
| **状态**：实时感知业务实体当前情况 | **认知层上下文构建**：从事件流重建状态 |
| **推理**：逻辑计划编译与分析 | **语义防火墙**：Parsing → Validation → Normalization |
| **行动**：触发具体业务指令 | **决策层执行器**：派发被批准的动作 |
| **反馈与调节**：回写本体，更新对象状态 | **审计 + 事件流**：写回事件链，修正下一轮上下文 |

关键差异：

- **Palantir 闭环**的操作对象是**业务实体**（订单、库存等），闭环周期为分钟到天级
- **Agent 事件循环**的操作对象是**认知意图**（文件修改、代码搜索等），闭环周期为秒到分钟级

但两者遵循相同的控制论结构——**"语义管道不是单向的。执行结果必须回流到语义层，成为下一轮决策的上下文。"**

## 七、工程含义：本体现状与下一步

### 7.1 uncode 当前的本体状态

uncode 中各层本体类型的实现现状：

| 本体层 | 存在形式 | 成熟度 |
|:---|:---|:---|
| **顶层本体** | `AgentEvent` 枚举 + `EventDetailLevel` | 高——32 变体 + 分层详略控制 |
| **领域本体** | 各工具模块的输入/输出类型 | 中——隐式定义，散落在工具模块中 |
| **任务本体** | 裁决器可接受动作列表 | 中——硬编码在裁决逻辑中，非声明式 |
| **应用本体** | Normalizer 输出的具体命令类型 | 低——Normalization 层不独立，散落在 `loop_engine` 和工具管线中 |

### 7.2 对照收口篇指出的差距

收口篇（`cognition-decision-driven-design.md` §6.3）指出 uncode 的三项差距：

1. **语义防火墙的 Normalization 层不独立** → 应用本体没有独立定义位置
2. **不确定性未显式类型化** → 任务本体缺少置信度/候选分支的属性定义
3. **缺少声明式护栏配置** → 本体约束与权限逻辑耦合在裁决代码中

这三点本质上对应了同一个问题：**本体没有被显式提升为架构中的独立层次。**

### 7.3 世界模型五原则的映射

⑬ §6.5 列出了世界模型的五个工程原则。这些原则对 uncode 的下一步有直接的指导意义：

| 世界模型原则 | 对认知显化范式的含义 | uncode 当前情况 |
|:---|:---|:---|
| **① 对象先于数据** | 先定义本体类型，再考虑如何存储和序列化 | 部分满足——有类型定义，但隐式分布 |
| **② 关系先于报表** | 先定义实体间的语义关系，再考虑查询展示 | 弱——关系和链接类型没有独立于实体定义 |
| **③ 规则先于 AI** | 护栏规则在本体中声明，而非在推理代码中硬编码 | 弱——规则硬编码在裁决逻辑中 |
| **④ 模拟先于执行** | 关键操作前应在本体副本中模拟效果 | 缺——无模拟能力 |
| **⑤ 权限先于功能** | 操作权限在类型定义中声明，而非在执行时临时检查 | 中——有 CancellationToken 等机制，但非声明式 |

### 7.4 建议方向

| 问题 | 本体视角的解 | 工程动作 |
|:---|:---|:---|
| Normalization 不独立 | 为应用本体创建独立模块（`uncode-ontology`） | 将各个 Normalizer 逻辑汇集到本体定义附近 |
| 不确定性未类型化 | 在任务本体定义中增加 `confidence: f64`、`candidates: Vec<T>` 等属性槽位 | 将不确定性元数据纳入类型定义，而非埋在调用链中 |
| 护栏不声明式 | 用本体约束（OWL-like 规则）替代硬编码裁决 | 护栏规则本身应当作为本体的"公理"来定义 |
| 关系未独立建模 | 为实体间关系创建显式的链接类型定义 | 参照 Palantir OMS 的 Link Type 设计 |
| 无模拟能力 | 引入决策前模拟机制，基于当前本体快照执行"假设分析" | 参照世界模型"模拟先于执行"原则 |

## 八、完整定位图

将 Palantir 三层架构与认知显化范式并排放置，可以看到两个体系在语义层面的完整对应：

```
认知显化与决策驱动设计           Palantir 三层架构             本体层
                          
┌────────────────────────┐   ┌────────────────────────┐   ┌────────────────────────┐
│   认知层                │   │   Dynamic Layer        │   │   领域本体 + 任务本体    │
│   ┌──────────────────┐ │   │   (世界如何决策)        │   │                        │
│   │ 上下文构建         │ │   │   规则/AI/权限/模拟     │   │   认知层引用领域概念     │
│   │ 提示词管理         │ │   └────────────────────────┘   │   防火墙引用任务约束     │
│   │ 不确定性管理       │ │                                │                        │
│   └──────┬───────────┘ │   ┌────────────────────────┐   │                        │
│          ↓              │   │   Kinetic Layer         │   ├────────────────────────┤
│   语义防火墙            │   │   (世界如何变化)        │   │   应用本体 + 动态本体    │
│   ┌──────────────────┐ │   │                        │   │                        │
│   │ Parser            │ │   │   Data Funnel          │   │   Normalizer → 标准化   │
│   │ Validator         │ │   │   Functions on Objects │   │   裁决器 → Action 验证   │
│   │ Normalizer        │ │   │   Actions (受控写)     │   │                        │
│   └──────┬───────────┘ │   └────────────────────────┘   │                        │
│          ↓              │                                │                        │
│   决策层                │   ┌────────────────────────┐   ├────────────────────────┤
│   ┌──────────────────┐ │   │   Semantic Layer        │   │   顶层本体              │
│   │ 提案接收  → 裁决   │ │   │   (世界是什么)         │   │                        │
│   │ 执行派发  → 审计   │ │   │   对象类型/属性/链接    │   │   AgentEvent 事件系统    │
│   └──────────────────┘ │   └────────────────────────┘   │                        │
└────────────────────────┘                                └────────────────────────┘
```

认知显化管道是"怎么转"，本体层是"转成什么"，Palantir 三层架构提供了一个被大规模验证的"运行时组织方式"。三者之间的关系：

| 层 | 认知显化范式角色 | Palantir 角色 | 本体类型 |
|:---|:---|:---|:---|
| **顶层/事件** | 不可变审计轨迹 | 对象数据库 + OMS 元数据 | 顶层本体 |
| **中间/语义** | 防火墙：推测 → 检查 → 归一化 | Semantic + Kinetic：映射 → 函数 → Action | 领域本体 + 任务本体 |
| **底层/决策** | 裁决 + 执行 | Dynamic：规则 → AI → 模拟 → 反馈 | 应用本体 + 动态本体 |

认知显化管道是"怎么转"，本体层是"转成什么"，两者在同一系统中**同时存在、彼此依赖**——管道依赖本体的类型定义来执行 Parsing/Validation/Normalization；本体依赖管道来填充运行时实例。没有本体的管道是无头苍蝇，没有管道的本体是死文档。

## 九、总结

| 问题 | 答案 |
|:---|:---|
| 认知显化转成什么？ | 转成本体实例。Parser/Validator/Normalizer 三层逐步将自然语言还原为符合本体定义的标准化结构。 |
| 本体在范式中什么位置？ | 独立于认知/决策之外的语义骨架层，被两者共同引用。认知层用它组织提示词，防火墙用它验证结构，决策层用它执行命令。 |
| Ground Truth vs Operational Truth 的工程对应？ | LLM 候选 = Operational Truth；防火墙验证和裁决 = Ground Truth 检查；事件流回写 = 写回机制。防火墙本质上是 Operational → Ground 的工业化转换流水线。 |
| 传统本体 vs 动态本体？ | 传统本体偏名词（实体+关系），动态本体将动词提升为独立类型——这与"决策作为第一公民"的主张完全一致。 |
| 本体四层 vs Palantir 三层？ | 前者按抽象粒度划分（通用→具体），后者按时序职责划分（定义→变化→决策）。两者互补，共同描述语义基础设施。 |
| uncode 欠缺什么？ | 本体没有被显式模块化，Normalization 层不独立、约束非声明式、关系未独立建模、无模拟能力。将本体提升为独立架构层次是最直接的"下一步"。 |
