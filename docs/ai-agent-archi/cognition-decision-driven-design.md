# 从 DDD 到认知显化与决策驱动设计：AI Agent 系统开发范式的演进与收口

> 本文是「AI Agent 架构治理」系列的**收口篇**。  
> 回答这样一个问题：

**在 LLM 驱动的 Agent 时代，软件架构范式究竟应该是什么样子？**

答案不是"抛弃 DDD"，也不是"仅用 CDD"，而是一种更完整的范式：**认知显化与决策驱动设计**。

这个范式的本质可以概括为一句话：

> **人机协同创作是一个愿景从模糊认知显化、再到 Agent 工程化实现的过程。决策的本质是模糊认知的显化。Agent Coding 不是 AI 替代，而是人机协同创作。**

LLM 负责模糊认知的生成——它把人的自然语言意图展开为候选方案、推理路径和备选动作，这些是"可能性"。系统架构负责模糊认知的显化——通过语义防火墙、裁决器、执行器和审计器，把模糊的可能性转化为确定的可执行命令和不可变的事件轨迹。事件流作为双向桥梁，将工程化实现的结果反馈回认知层，形成下一轮模糊→显式的输入。

在工程中，显化过程由 Harness Engineering（编排、工具、记忆、观测、进化）和 7 种架构范式（事件驱动、事件溯源、约束设计等）共同支撑。三个独立的外部研究——DOP 论文（决策第一公民）、Autodesk 认知架构（闭环协调）、Anthropic Harness（模型外的工程）——从不同路径验证了这一范式的正确性。

## 引言：范式断层的二十年

2004 年，Eric Evans 出版《领域驱动设计》。他的核心假设清晰而坚定：**软件系统的复杂性来自业务领域，而业务规则是可表达、可建模、可验证的。** 在这个世界里，一个"确定性系统"是默认的——同样的输入，同样的上下文，应该得到相同的输出。

二十年后的今天，AI Agent 系统把这个假设撕开了。LLM 驱动的 Agent 不再只是"执行 if-else"的规则机器，而是"生成下一步动作"的认知体。同样的任务，不同时刻、不同上下文，可能会产生不同的计划、不同的执行路径，甚至不同的"理解方式"。

于是我们有了第一次理论进化：CDD（认知驱动设计），把 DDD 从"规则驱动"推进到"认知驱动"。

但 CDD 本质上只做对了一半：它告诉我们"要为不确定性留出结构性空间"，却没有回答最工程化的问题——**当 LLM 产生几十个候选动作时，谁来裁决？怎么裁决、怎么记录、怎么回滚？系统的第一公民到底是什么？**

答案不在认知层，在决策层。

这就是本文的核心命题：**AI Agent 系统开发需要一个新范式——它不是单纯的"认知驱动"，而是"认知与决策驱动"的。** 在这个范式中，工作流、状态机、事件驱动、CQRS、事件溯源、约束式设计和多 Agent 协作，构成它的"综合治理工具箱"。

## 第一部分：DDD 的局限——它没有错，只是领域变了

### 1.1 经典 DDD 的四重前提

回顾一下 DDD 为什么能在传统业务系统中成功：

| 前提 | DDD 的应对 | 传统系统的验证方式 |
|:---|:---|:---|
| 业务规则**可表达** | 实体、值对象、规约模式 | 编译通过、单元测试通过 |
| 状态转换**确定** | 聚合保证一致性边界 | 同样的输入，同样的输出 |
| 事务边界**短** | 聚合内强一致性、聚合间最终一致性 | 毫秒级事务 |
| 领域语言**统一** | 限界上下文 + 通用语言 | 团队共识、文档对齐 |

这套模型在电商、银行、ERP 中运行了二十年，没出大问题。因为业务世界确实是这样运行的——"一个订单的总价"不会随机波动，"一个账户的余额"不会因为同样的计算得到两个不同的值。

### 1.2 AI Agent 打破了什么

但当系统的核心决策者从"if-else"变成 LLM，四重前提全部失效：

| DDD 前提 | AI Agent 的挑战 | 本质原因 |
|:---|:---|:---|
| 规则可表达 | 大量逻辑存在于提示词字符串中，无法被类型系统检查 | 领域逻辑脱离了编程语言的治理 |
| 状态确定 | 同样的任务，不同时刻可能产生不同的计划和执行路径 | LLM 的采样机制决定了非确定性 |
| 事务短 | 一个任务从"理解需求"到"完成修改"可能持续数分钟 | 认知过程不是事务，是旅程 |
| 语言统一 | 同一个概念在 LLM 输出中可能以十种不同的自然语言形式出现 | 自然语言不承诺语义一致性 |

这就是系列第一篇（`ddd-ai-agent.md`）详细论述的"水土不服"。但关键的判断不是"DDD 没用了"，而是"**DDD 需要换一种使用方式**"。

## 第二部分：CDD 的贡献与不完整

### 2.1 CDD 做对了什么

系列第四部分提出了 CDD（认知驱动设计）作为 DDD 在 AI 时代的演化方向。它的核心贡献是把 DDD 的几个概念"认知化"：

| DDD 概念 | CDD 重定义 | 价值 |
|:---|:---|:---|
| 限界上下文 | → 认知边界：隔离确定性计算、概率性推理和涌现行为 | 防止 LLM 污染核心状态 |
| 聚合 | → 快照验证 + 事件流 | 长流程下的一致性替代方案 |
| 防腐层 | → 语义防火墙：Parsing → Validation → Normalization | LLM 输出永远不直接进入领域层 |
| 领域事件 | → 事件认知溯源：记录决策轨迹，支持回放和优化 | 从"通知"升级为"核心产品" |

这些调整方向是对的。uncode 项目的工程实践证明了这一点——它的限界上下文隔离、事件系统、护栏体系，都是在 CDD 方向上做扎实了的。

### 2.2 CDD 没回答的问题：谁在做决策？

CDD 的根本问题在于定位模糊。它告诉我们"要关注认知"，却没有说清楚：系统的"第一公民"到底是什么。

- 在 DDD 中，第一公民是"业务规则"。所有建模都围绕规则展开：规则在哪里、怎么变、怎么验证。
- 在 CDD 中，第一公民被模糊地指向"认知过程"。但这其实回到了"LLM 如何想"，而不是"系统如何约束它"——而后者才是架构师能直接控制的范畴。

uncode 的工程实践暴露了一个关键事实：**uncode 最强的工程力，不是"认知管理"，而是"决策治理"。**

- Phase 守卫禁止并发运行 → 这是**决策排他性**
- MAX_TURNS=50 硬限 → 这是**决策容量约束**
- terminate AND 语义 → 这是**决策完成条件**
- CancellationToken 在 5 个检查点介入 → 这是**决策可中断性**
- 事件链完整记录每步决策 → 这是**决策审计**

这些不是"认知建模"，这些是"决策建模"。

CDD 的问题不在于错了，而在于它把决策层的工程实践错误地归到了认知层名下。**"认知驱动"这个名字本身就暴露了它的偏向——它把系统的全部复杂性归到了认知侧，没有为"决策"单独设立第一公民地位。**

## 第三部分：认知显化与决策驱动设计——一个新范式

### 3.1 核心定义

> **认知显化与决策驱动设计是一套 AI Agent 系统的架构范式。它的本质是：人机协同创作是一个愿景从模糊认知显化、再到 Agent 工程化实现的过程。决策的本质是模糊认知的显化。Agent Coding 不是 AI 替代，而是人机协同创作。**

拆解这个定义：

**一个本质**：

- **决策 = 模糊认知的显化**。系统的每一步操作——从 LLM 自然语言输出到结构化命令，从候选提案到被批准的执行，从原始结果到可训练的轨迹——都是一个"模糊→显式"的原子转换。整个系统的架构就是一条认知显化流水线。

**两个阶段**：

- **阶段 1：模糊认知的显化**（认知层 → 语义防火墙）。LLM 的自由文本、自然语言提案、未验证的候选方案，经过 Parsing → Validation → Normalization 逐步显化为确定性命令。这是"显化"。
- **阶段 2：显式认知的工程化实现**（决策层 → 治理层）。被批准的确定性命令经过执行、审计、评估和进化，转化为可观测、可审计、可优化的工程产物。这是"工程化实现"。

**一个原则**：

- **每一步都是模糊→显式的原子转换**。`ActionProposal → ParsedAction → ValidatedAction → NormalizedAction → ApprovedAction → ExecutionResult → AgentStep → EvaluationScore`——八个原子转换串联成一条完整的认知显化链。每个箭头只做一件事：让信息更确定、更结构、更可验证。

**三个独立的外部验证**：

- **DOP 论文**（arXiv 2604.05203）：Aporia 的 Decision Bank 将隐式设计决策显化为可编辑的第一公民对象，用户理解准确度提升 5x。
- **Autodesk 认知架构**（2026-05）："Perception is not preprocessing. It is a representational pipeline."——感知本身就是模糊→显式的表征管道。
- **Anthropic Harness**（2026-05）："The harness matters as much as the model."——Harness 是将模型模糊输出显化为可靠软件的工程基础设施。

### 3.2 与 DDD 的关系：进化，不是替代

```
         DDD (2004)                    CDD (2024)               认知显化与决策驱动设计
    ┌──────────────┐           ┌──────────────┐           ┌─────────────────────────┐
    │              │           │              │           │  认知层 (Cognitive)      │
    │  业务规则     │           │  认知模型     │           │  ┌─────────────────┐    │
    │  = 第一公民   │  ──→     │  = 第一公民   │  ──→     │  │ 上下文构建       │    │
    │              │           │              │           │  │ 提示词管理       │    │
    │  状态驱动     │           │  认知驱动     │           │  │ 不确定性管理     │    │
    │              │           │              │           │  └─────────────────┘    │
    └──────────────┘           └──────────────┘           │          ↕              │
                                                          │    语义防火墙           │
                                                          │          ↕              │
                                                          │  决策层 (Decision)      │
                                                          │  ┌─────────────────┐    │
                                                          │  │ 决策提案 (接收)   │    │
                                                          │  │ 决策裁决 (验证)   │    │
                                                          │  │ 决策执行 (派发)   │    │
                                                          │  │ 决策审计 (记录)   │    │
                                                          │  └─────────────────┘    │
                                                          │  决策 = 第一公民        │
                                                          └─────────────────────────┘
```

**不是推倒重来，而是补齐了缺失的一半。** DDD 的限界上下文、聚合、防腐层、领域事件——这些概念没有消失，它们在决策层找到了新的角色。

### 3.3 两层模型的详细展开

#### 认知层：LLM 的自由之地

认知层解决一个问题：**"接下来可以做什么？"** 它不裁决，只生成候选。

| 认知层次组件 | 职责 | DDD 映射 |
|:---|:---|:---|
| **上下文构建器** | 从事件流重建会话历史、注入环境状态、管理记忆与检索 | 仓储的"读"面 |
| **提示词即领域语言** | 将系统约束、工具描述、任务目标编码为 LLM 可理解的指令 | 通用语言的"AI 受众"版 |
| **不确定性管理器** | 对生成不确定性(candidates+rerank)、认知不完全性(context enrichment)、执行不确定性(retry/saga)分别调度 | 新领域对象 |

认知层的输出**不是**可执行的命令——它是候选方案（`ProposedAction[]`），携带着置信度、推理链和备选路径。

#### 决策层：系统的铁律之地

决策层解决一个问题：**"哪些可以做，谁来做，做了什么，结果怎样？"**

这是新范式的核心——也是当前多数 Agent 系统最薄弱的一环。

| 决策阶段 | 职责 | 对应的 DDD 概念升级 |
|:---|:---|:---|
| **提案接收** | 通过语义防火墙将 LLM 候选转换为结构化 `ProposedAction` | 防腐层 → 语义防火墙 |
| **合法性裁决** | 护栏系统（policy + guardrails）验证动作是否被允许 | 规约模式 → 行为护栏 |
| **权限检查** | 资源边界、工具白名单、频率限制 | 聚合 → 决策授权单元 |
| **执行派发** | 将被批准的 `ApprovedAction` 派发到工具执行器，管理并行/串行/terminate | 领域服务 → 执行编排器 |
| **结果捕获** | 将 action、observation、feedback 打包为 `AgentStep` 事件 | 领域事件 → 决策轨迹 |
| **审计回放** | 提供任意历史时刻的决策链重建 | 事件溯源 → 决策审计 |

#### 语义防火墙：唯一可以穿过两层的东西

在大段的自然语言和自由文本面前，语义防火墙只允许一种东西通过：**结构化语义。**

```
LLM 自然语言："我觉得应该改一下 auth.ts，加上 2FA 的模板"
         ↓
  Parser   →  { action: "modify_file", target: "src/auth.ts", intent: "add_2fa", confidence: 0.82 }
         ↓
Validator  →  { approved: true, normalized_target: "src/auth/mod.ts", guardrails: [...] }
         ↓
Normalizer →  ModifyFileCommand { file: "src/auth/mod.ts", operation: "append", scope: "two_factor_auth" }
         ↓
      进入决策层
```

认知层永远不知道决策层的裁决逻辑。决策层永远不接触认知层的自然语言。**唯一的握手协议是结构化命令 + 结构化反馈。**

### 3.4 决策作为第一公民：这意味着什么

范式命名中，"决策"排在"认知"之后，但在工程上**决策层是更重、更硬、更需要架构投入的一层**。

认知层可以换模型、换提示词、换推理策略——只要输出协议不变，决策层不感知。
决策层的变化（加护栏、改权限、换事件存储）要求更高的可靠性保证，因为它直接决定了系统会不会做错事。

这种不对称性反映了一个根本事实：**LLM 是可以替换的，但决策的正确性是必须保证的。** 认知提供可能性，决策承担后果——两者之间是"可以犯错"和"不能犯错"的分界线。

## 第四部分：综合治理与 Harness Engineering——范式的操作层

### 4.1 范式是设计平面，治理是操作平面

认知显化与决策驱动设计告诉你**系统该怎么分**。但它不告诉你**系统该怎么跑**。

运行时治理有两个子层：

| 子层 | 定位 | 内容 | 范围说明 |
|:---|:---|:---|:---|
| **Harness Engineering** | 工程实践层 | 编排器、工具注册、分层记忆、可观测性、自适应进化 | Agent **内部**架构——"怎么搭" |
| **7 种架构范式** | 模式工具层 | 事件驱动、事件溯源、约束设计等 | 跨系统的通用模式——"用什么模式" |

> **注意**：Anthropic 在 Claude Code 博文中提出的 Harness 概念（CLAUDE.md、hooks、skills、plugins、MCP）
> 属于**开发者界面层**——开发者如何配置和治理 Agent。本文的 Harness Engineering 指代 Agent 的内部工程架构。
> 详见 `docs/others/Harness_Engineering_Archi.md` 附注。

**Harness Engineering 是治理层的工程实现**。当我们说"决策层裁决"时，Harness Engineering 告诉我们裁决器怎么设计；当我们说"护栏"时，Harness Engineering 告诉我们工具如何注册、权限怎么检查。

这不是两个独立的概念——Harness Engineering **从属于**认知显化与决策驱动设计的治理层，是它落地的工程方法。

#### Harness Engineering 五模块在范式中的位置

| Harness 模块 | 范式中的位置 | uncode 对应 |
|:---|:---|:---|
| **编排与状态管理** | 决策层 | `decision/adjudication.rs` + `AgentHarnessPhase` + `ProposalAccumulator` |
| **工具治理与安全** | 决策层 SemanticFirewall | `decision/firewall.rs` + `tools/registry.rs` + `tool_permission.rs` |
| **分层记忆** | 认知层 | `WorkingMemory` → `EpisodeMemory` → `MemoryManager` → `SessionStore` |
| **可观测性与评估** | 治理层事件系统 | `AgentEvent` 32 变体 + `EventDetailLevel` + `decision/evaluator.rs` + `FeedbackBridge` |
| **自适应与进化** | 治理层 | `EvolutionEngine` + `HarnessMutation` + `GuardrailConfig` |

#### 7 种架构范式在 Harness 中的体现

下面 7 种范式仍然是操作平面的工具——它们与 Harness Engineering 是不同粒度的治理：

| 范式 | 在认知显化与决策驱动设计中的位置 | 解决的问题 |
|:---|:---|:---|
| **事件驱动架构** | 认知层 ↔ 决策层的通信骨干 | 认知输出如何触发决策过程，决策结果如何反馈给认知上下文 |
| **事件溯源** | 决策层的持久化策略 | 每一次裁决、执行、回滚的完整轨迹如何存储和回放 |
| **约束式设计** | 决策层的护栏实现方式 | 用什么机制保证"不被允许的动作永远不会被执行" |
| **有限状态机** | 决策层的生命周期管理 | Agent 的 idle/thinking/acting/waiting/failed 状态如何互斥和转换 |
| **工作流编排** | 认知层 + 决策层的任务分解 | 复杂多步骤任务如何被拆分为可管理的单元 |
| **CQRS** | 决策层的读写分离 | 决策写入（严格）和状态读取（灵活）如何独立演进 |
| **多 Agent 协作** | 认知层的横向扩展 | 复杂场景下如何分工、制衡、协作 |

**关键洞察**：这 7 种范式不是备选方案——它们各司其职，在同一系统中**同时存在**。事件驱动是通信机制，事件溯源是存储策略，约束设计是安全策略，状态机是生命周期策略——它们是不同层面的治理，不是互相替代。

### 4.2 综合治理的"铁三角"

在实践中，有三个范式构成 AI Agent 治理的**稳定三角形**：

```
                    事件驱动
                    (通信骨干)
                      ╱  ╲
                     ╱    ╲
                    ╱      ╲
              事件溯源      约束设计
             (持久化)      (安全边界)
```

- **事件驱动**保证认知与决策之间的信息无损流动
- **事件溯源**保证每一条决策都有据可查、可回放、可审计
- **约束设计**保证错误决策不会变成系统事故

一个没有事件驱动的 Agent 系统是**盲的**（不知道发生了什么）。
一个没有事件溯源的 Agent 系统是**失忆的**（不知道为什么这么做）。
一个没有约束设计的 Agent 系统是**危险的**（什么都能做）。

uncode 在这三条上的工程化程度最高，这不是巧合——因为它们构成了治理的"最小可行集合"。

把设计平面、Harness Engineering 和 7 种范式拼在一起，全景是：

## 第五部分：设计原则与工程实践

### 5.1 七条设计原则

基于认知显化与决策驱动设计的核心主张——**决策的本质是模糊认知的显化**——可以提炼出七条可操作的设计原则：

0. **每一步都是模糊→显式的原子转换**。系统中的每个箭头——`ActionProposal → ParsedAction → ValidatedAction → NormalizedAction → ApprovedAction → ExecutionResult → AgentStep`——只做一件事：让信息更确定、更结构、更可验证。如果你无法用"这一步把什么从模糊变成了显式"来描述一个模块的职责，它就不属于认知显化链。

1. **认知与决策强制分离**。LLM 调用和系统裁决永远不在同一个代码模块中。如果一个函数既调 LLM 又做权限判断，它就已经违反了这条原则。

2. **自然语言止于防火墙**。任何自然语言内容在进入决策层之前必须被解析为结构化语义。决策层不接受非结构化文本作为输入。

3. **决策即事件**。每一次裁决、每一次执行、每一次回滚，都必须以事件的形式记录下来。没有事件的决策等于没有发生。

4. **护栏优先于智能**。先定义不可逾越的边界，再允许 LLM 在边界内自由发挥。给 LLM 更多自由的前提是，你做足了限制。

5. **事件流是双向通道**。事件不仅要向下游流向审计和观测，也要向上游流回认知层的上下文——形成"行动 → 观察 → 反馈 → 下次行动"的闭环。

6. **治理层与范式层正交**。7 种治理范式可以独立选择、组合和替换，不绑定于任何一个范式。约束设计不需要依赖事件溯源；CQRS 不需要依赖多 Agent。

### 5.2 从零开始的落地顺序

如果你从零开始构建一个遵循此范式的 Agent 系统，推荐的顺序不是"先认知后决策"，恰恰相反——**先决策后认知**。

```
阶段 1：铁三角治理
  │  事件驱动 ──→ 事件溯源 ──→ 约束设计
  │  这三样不依赖 LLM，可以先搭建并通过 mock LLM 验证
  │
  ▼
阶段 2：决策层
  │  提案接收 ──→ 裁决器 ──→ 执行器 ──→ 审计器
  │  此时已有完整的"接收 → 裁决 → 执行 → 记录"闭环
  │
  ▼
阶段 3：防火墙 + 认知层
  │  语义防火墙 + 上下文构建器 + 提示词管理 + 不确定性管理
  │  此时 LLM 才开始参与，但它的输出已经有了完整的决策宿主管道
  │
  ▼
阶段 4：高级治理
    工作流编排 + 状态机 + CQRS + 多 Agent 协作
    这些在基础治理稳固之后才引入，用于解决更复杂的场景
```

这个顺序违反直觉——大多数人会想"先接上 LLM，让它能动起来再说"。但实践证明，"能动起来"和"动了不出事"之间，差的正是阶段 1 和 2。

## 第六部分：与现有范式和项目的对话

### 6.1 与 DDD 的关系：继承了战略，重建了战术

认知显化与决策驱动设计**完全继承了 DDD 的战略工具**：限界上下文用来划认知/决策边界，上下文映射用来定义边界间的交互协议，通用语言用来保证同一概念在 LLM 和代码中有一致的语义。

**战术层面则被重建了**：聚合变成了决策授权单元而非事务单元，防腐层变成了语义防火墙而非 DTO 转换器，领域事件变成了决策轨迹而非通知消息。

这是"进化"的本意——战略思想不变，战术实现重写。

### 6.2 与 CDD 的关系：补齐了缺失的一半

CDD 对了一半。**"认知驱动"** 这个命名本身暴露了它的偏向——它把系统的全部复杂性归到了认知侧。但 uncode 的工程实践反复告诉我们：**认知是 LLM 的事，决策才是架构师的事。**

认知显化与决策驱动设计不是推翻 CDD，而是把 CDD 隐含但未说出口的"决策层"从幕后拉到了台前，给定它独立的第一公民地位。

### 6.3 与 uncode 的关系：理论的验证者和超越者

uncode 是当前最能体现这个范式的开源项目。它的限界上下文隔离、事件系统、护栏体系都是"认知与决策驱动"的活体实现。

但 uncode 也暴露了当前实现的边界：语义防火墙的 Normalization 层不独立、不确定性未显式类型化、缺少声明式护栏配置——这些正是范式升级后指出的"下一步"。

**uncode 验证了这个范式是可行的，同时也证明了还需要继续走。**

### 6.4 与 Anthropic/OpenAI 官方 Agent 框架的差异

Anthropic 的"Think → Plan → Act"循环和 OpenAI 的 Swarm/Assistants 提供了初步的认知-行动分离思路。但它们倾向于把"决策"当作 LLM 推理的延伸——LLM 自己决定做什么、怎么做。

认知显化与决策驱动设计的关键差异在于：**它不信任 LLM 的决策能力。**

它认为 LLM 的角色严格限定在"生成候选方案"。决定哪些方案被批准、以什么顺序执行、执行结果如何反馈——这些全部由系统代码层独立裁决。这是从"Agent = 智能体"到"Agent = 被治理的智能体"的根本立场转变。

## 结论：一个可命名、可教学、可实现的范式

回到本文的起点：**在 LLM 驱动的 Agent 时代，软件架构范式究竟应该是什么样子？**

- **DDD 不能直接照搬**——它默认的"确定性世界"已经不存在。
- **CDD 不够**——它只回答了"认知侧"，却把"决策层"藏在 Harness 工程实践里没说清楚。
- **7 种架构范式是操作工具**，不是"设计平面"。

因此，完整的答案是：

> **认知显化与决策驱动设计 + Harness Engineering + 7 种综合治理范式。**

其中：

- **认知层** = LLM 的"舞台"。回答"接下来可以做什么？"
- **决策层** = 系统的"铁律"。回答"哪些可以做，做了什么，结果怎样？"
- **语义防火墙** = 两者之间的"唯一通道"
- **事件流** = 两者之间的"双向信息桥梁"
- **Harness Engineering** = 治理层的工程实践（编排、工具、记忆、观测、进化五模块）
- **7 种治理范式** = 治理层的模式工具（事件驱动、事件溯源、约束设计、状态机、CQRS、工作流、多Agent协作）

这五个组件，构成了一个**可命名、可教学、可实现**的完整范式地图。

它不是"对 DDD 的否定"，而是"DDD 战术模式在概率性世界里的自然演化"。它吸收了 CDD 的"认知意识"，但补上了 CDD 缺失的"决策"这一半。

如果要将这个范式概括为一句话：

> **人机协同创作是一个愿景从模糊认知显化、再到 Agent 工程化实现的过程。决策的本质是模糊认知的显化。Agent Coding 不是 AI 替代，而是人机协同创作。**

在这个公式中，LLM 负责模糊认知的生成，语义防火墙负责将模糊显化为结构，决策层负责将显式认知 Agent 工程化实现，事件流负责将工程化结果反馈回认知层——形成一个"模糊→显式→工程化→反馈→下一轮模糊"的闭环。这不是一个纯理论的构造——uncode 已在用 Rust 编译运行这个范式的内核，而 DOP 论文、Autodesk 认知架构和 Anthropic Harness 从三个独立路径验证了它的正确性。

## 附注：决策层与 Harness Engineering 的关系

读者可能会注意到，"决策层"与近年来 Agent 工程领域流行的 **Harness Engineering** 概念有很强的共鸣。这里澄清两者的关系——它们高度相关，但不等价。

### 共同点

两者描述的是同一块工程实践的两种视角。Pi（`@earendil-works/pi-agent-core`）、uncode（`uncode-agent`）的 `AgentHarness` 本质上实现的就是决策层的工作——工具管线、安全护栏、状态管理、事件记录。

### 关键差异

**1. 粒度不同：Harness 是"一团"，决策层是"四段"**

Harness Engineering 习惯把工具执行、权限检查、状态转换、事件记录作为一个集成整体讨论——"Harness 负责所有非 LLM 的事"。从工程实践角度看这很自然，但对架构设计来说，这个粒度太粗了。

决策层将同一块实践拆成四个正交阶段：

| 决策层阶段 | Harness Engineering 中的对应 | 拆开的理由 |
|:---|:---|:---|
| 提案接收 | 工具调用的参数解析 | 独立于裁决——解析失败应与权限逻辑解耦 |
| 裁决 | 护栏、权限检查 | 纯函数，应可独立单元测试 |
| 执行派发 | 工具执行管线 | 关心并行/串行/terminate 语义，与裁决无关 |
| 审计 | 事件记录、日志 | 关心持久化和回放，应对执行无侵入 |

uncode 的架构评价暴露了这种粒度差异的实际后果——它的 Normalization 层（提案接收的最后一步）散落在 `loop_engine` 和工具管线中而不够独立。如果说"这是 Harness 的事"，这个架构问题被模糊化。如果说"这是决策层提案接收阶段的职责"，问题就变得可精确定位和修复。

**2. 范式地位不同：附属品 vs 第一公民**

在 Harness Engineering 的叙事中，Harness 是**附属品**——模型是主角，Harness 是给它套上缰绳的辅助设施。"Harness"这个词本身就暗示了"约束性配件"的含义。

在认知显化与决策驱动设计中，决策层是**不亚于认知层的第一公民**。LLM 可以换，决策的正确性必须保证。这不是语义上的抬举——它改变了设计优先级：

- Harness Engineering 视角：先接 LLM，再慢慢加护栏
- 决策层视角：先搭决策基础设施，再接 LLM（就像本文 5.2 的落地顺序）

**3. 概念边界不同**

Harness Engineering 是一个**实践模式**——它描述"怎么搭 Agent 基础设施"，但不要求一个事先的范式判断。

决策层是一个**范式概念**——它的成立依赖于先验判断：**认知和决策必须作为两个正交层次来设计。**

你可以不认同认知显化与决策驱动设计这套完整范式，但仍然可以说"我的 Agent 有一个 Harness"。但一旦你接受了"认知与决策必须分离"的前提，Harness Engineering 就自然落入范式地图的决策层位置。

### 一句话总结

> **Harness Engineering 告诉你"怎么做"；决策层告诉你"为什么要这样做，以及它应该在设计平面上占据什么位置"。** 两者不是替代关系——Harness Engineering 是决策层的工程语言翻译。面向工程团队沟通时说 Harness，做架构设计和范式定义时说决策层。
