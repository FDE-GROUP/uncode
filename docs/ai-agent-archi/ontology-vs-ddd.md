# 本体论与领域驱动设计：两种语义治理范式的对比

> 本文是「AI Agent 架构治理」系列的**对比篇**，位于本体论基础篇（⑬）之后。
>
> 回答这样一个问题：**本体论和领域驱动设计（DDD）之间的关系是什么？它们各自服务于什么目的，在 AI Agent 时代如何协同？**

本体论和 DDD 都关注"如何理解和表达业务世界的结构"，但两者的出发点和工具集有根本差异。本文从九个维度逐一对比，然后讨论它们在认知显化与决策驱动设计范式中的协作关系。

---

## 一、九维对比总表

| 维度 | 领域驱动设计 (DDD) | 本体论 (Ontology) | 差异本质 |
|:---|:---|:---|:---|
| **学科起源** | 软件工程方法论（Eric Evans, 2004） | 哲学分支（~2500 年），信息系统应用（Gruber, 1993） | 工程方法 vs 认知学科 |
| **核心问题** | "如何将业务规则建模为可执行的软件？" | "什么存在？它们之间有什么属性与关系？" | 怎么做 vs 是什么 |
| **抽象层次** | 战略（团队/组织边界）→ 战术（代码/对象）两层 | 顶层（跨领域）→ 领域（行业）→ 任务（动作）→ 应用（系统）四层 | 组织视角 vs 概念视角 |
| **形式化手段** | 代码模式（Entity, Aggregate, Service）+ 团队公约 | OWL/RDF 逻辑公理（继承、约束、基数）——机器可读 | 自然语言共识 vs 形式化推理 |
| **动词的地位** | 领域服务 + 领域事件——行为封装在对象之外 | 传统：动词是对象属性的"角色名"；动态：动词是第一公民类型 | 行为的附属 vs 独立 |
| **变更管理** | 重构代码 + Event Storming 对齐认知 | 版本化本体 + 兼容性检查（规范独立于代码演化） | 代码驱动 vs 规范驱动 |
| **跨系统交互** | 上下文映射 + 防腐层（ACL）——关注通信协议 | 引用同一顶层/领域本体——关注语义一致性 | 接口对齐 vs 语义对齐 |
| **与 LLM 的关系** | 不适配——确定性世界假设，概率性输出无法通过类型系统检查 | 适配——语义防火墙的目标模式，Parser/Validator/Normalizer 三层逐步还原为本体实例 | 假设确定性 vs 包容概率性 |
| **在范式中的角色** | 提供战略边界（限界上下文、通用语言），范式继承战略重建战术 | 提供语义骨架（类型系统、约束规范、动作注册表） | 边界治理 vs 语义治理 |

## 二、维度逐项展开

### 2.1 学科起源：工程方法 vs 认知学科

**DDD** 诞生于 2004 年，Eric Evans 在公司里观察到大量项目失败于"业务方和开发方说不同的语言"。它的解决思路是工程化的：在代码中建立领域模型，让代码成为业务规则的可靠表达。DDD 是一套**软件工程方法论**。

**本体论**起源于亚里士多德对"存在"的分类（范畴论），在信息系统中由 Gruber 在 1993 年给出工程定义——"对共享概念的形式化、显式的规范"。它是一套**语义认知框架**，不关心代码怎么组织，只关心概念怎么定义、怎么关联、怎么约束。

两者的出发点是正交的：DDD 问"怎么写代码让业务不出错"，本体问"业务中说的东西到底是什么"。

### 2.2 抽象层次：两层 vs 四层

DDD 的两层：

```
战略层          战术层
组织/团队边界 → 代码/对象建模
(限界上下文)    (实体、值对象、聚合、服务、仓储)
```

本体的四层：

```
顶层本体         领域本体          任务本体         应用本体
跨领域通用概念 → 行业专属概念 → 动作/过程概念 → 系统具体实例
(时间、空间、   (客户、SKU、   (发起支付、    (双十一结算规则、
 对象、事件)     仓储)          风控验证)      京豆抵扣约束)
```

DDD 的"领域"对应本体的"领域本体"层——两者都关注特定业务领域的概念建模。但本体多了三个 DDD 没有的维度：

- **顶层本体**：保证跨领域系统间的最底层交互协议（AgentEvent 32 变体就是一种顶层本体）
- **任务本体**：独立于领域的动作类型，可被多个领域复用（支付动作可被电商和缴费系统共用）
- **应用本体**：最细粒度的系统专有规则，直接驱动执行逻辑

### 2.3 形式化程度：自然语言共识 vs 机器可读公理

这是最本质的差异之一。

DDD 的形式化最终落地为**代码**：

```rust
// DDD：实体 + 方法 + 单元测试
struct Order {
    items: Vec<OrderItem>,
    status: OrderStatus,
}
impl Order {
    fn add_item(&mut self, item: OrderItem) {
        // 业务规则写在方法体中，通过单元测试验证
        assert!(self.status == OrderStatus::Draft);
        self.items.push(item);
    }
}
```

本体的形式化落地为**逻辑公理**，可在 OWL/RDF 中表达：

```xml
<!-- OWL：机器可读的本体公理 -->
<Class IRI="#Order"/>
<DataProperty IRI="#hasStatus">
  <Domain IRI="#Order"/>
  <Range IRI="#OrderStatus"/>
</DataProperty>
<Restriction>
  <!-- Order.status 的值必须在 OrderStatus 枚举中 -->
</Restriction>
```

在纯人工团队中，DDD 的形式化程度足够——代码审查 + 单元测试 + 团队对齐。但在 AI Agent 场景中，LLM 生成的不是代码而是自然语言，DDD 的形式化手段（代码类型系统）不再覆盖 LLM 的输出。本体提供的 OWL 级形式化可以填补这个缺口——Parser/Validator/Normalizer 三层本质上就是在运行时执行 OWL 级的类型、约束、关系检查。

### 2.4 动词的地位：附属 vs 独立

DDD 中的行为有三种表达方式：

| DDD 概念 | 动词表达 | 问题 |
|:---|:---|:---|
| **实体方法** | `order.add_item(item)`——动词是实体的方法 | 动词寄生在实体上，不适合跨实体的业务操作 |
| **领域服务** | `PaymentService.process(payment)`——动词是 service 的方法 | 动词在无状态 service 中，类型信息弱 |
| **领域事件** | `OrderPlaced { order_id, items }`——动词是过去时的"已发生" | 事件记录结果，不适合前置裁决 |

本体传统上也是名词优先：`Person -[employed_by]-> Company` 中"employed_by"是对象属性（Object Property），不是独立类型。

**动态本体**（Palantir）打破了这一点：动词被提升为独立的第一公民类型。`HireCommand { employee, company, date, contract_type }`——它是一个可以被实例化、验证、执行、审计的独立类型。

这对 Agent 系统有直接的工程意义。⑫篇 §6.2 已经指出：**决策层裁决的是动作，不是实体。** 裁决器不需要理解"文件"是什么，它只需要检查 `ModifyFileCommand { file, operation, content }` 是否满足权限规则和参数约束。动词的独立化是"决策作为第一公民"在语义层面的工程实现。

### 2.5 与 LLM 的关系：DDD 的四重失效

收口篇（⑤ §1.2）定义了 DDD 在 AI Agent 时代失效的四重前提。本体对这四重失效的应对方式：

| DDD 失效的前提 | DDD 的应对 | 本体的应对 |
|:---|:---|:---|
| 规则可表达——规则在提示词中，无法被类型系统检查 | 无解（代码不覆盖提示词） | Parser 对照本体类型表解析——已知类型通过，未知类型拒绝 |
| 状态确定——LLM 可能产生不定计划 | 无解（非确定性是模型特性） | 本体不要求确定性，只要求"如果某个命题被当作真，它的结构必须满足约束" |
| 事务短——长的认知过程不是短事务 | 快照验证 + 事件流 | 本体实例化不依赖事务，每次 Parser/Validator/Normalizer 调用是独立的 |
| 语言统一——同一概念多种表述 | 团队对齐（不覆盖外部输入） | Normalizer 的职责之一：`"test_*" → "test/*"`——多表述归一化为标准本体实例 |

关键区别在于：**DDD 试图在前提层面消除不确定性，本体在后果层面约束不确定性。** DDD 的前提"业务规则可表达"意味着系统**默认**输入是合法的；本体的前提"输出必须满足本体约束"意味着系统**默认**输入是不合法的，必须经过验证。

### 2.6 变更管理：代码重构 vs 版本化演进

DDD 的变更管理依赖**代码重构**：

```
识别新概念 → 修改实体/聚合 → 改 Repository → 迁移数据库 → 更新测试
```

这个过程天然耦合了业务概念（"订单加了新状态"）和技术变更（"改数据库 schema"）。

本体的变更管理是**版本化规范**的：

```
本体 V1: OrderStatus = { Draft | Confirmed | Shipped }
                    ↓
本体 V2: OrderStatus = { Draft | Confirmed | Paid | Shipped | Cancelled }
                    ↓
兼容性检查: V1 所有实例在 V2 中是否仍合法？(是 ✓)
            V2 的新状态是否被所有消费者理解？(需要确认)
```

本体规范可以比代码变更更早、更独立地演进。团队可以先就新本体达成共识，再决定何时迁移代码。这在 AI Agent 场景中尤其有价值——当你需要为一个新工具（如 `web_search`）声明其输入/输出类型时，首先在任务本体注册表中添加 Action Type，然后实现代码——而不是反过来。

## 三、映射：DDD 战术概念在 AI 时代的本体对应

⑤ §6.1 指出"DDD 的战术层面被重建了"。借助本体论的视角，可以更精确地描述这种重建：

| DDD 战术概念 | DDD 原意 | 在认知显化范式中的归宿 | 本体对应 |
|:---|:---|:---|:---|
| **实体**（Entity） | 有唯一标识的领域对象 | 仍为实体，但由语义防火墙保护 | 领域本体中的 ObjectType |
| **值对象**（Value Object） | 无标识的属性集合 | 仍为值对象，语义更丰富 | 领域本体中的 Property 组合 |
| **聚合**（Aggregate） | 事务一致性边界 | → **决策授权单元**——护栏检查权限 | 应用本体中的约束公理 |
| **领域服务**（Domain Service） | 无状态的业务操作 | → **执行编排器**——派发被批准的动作 | 任务本体中的 Action Type |
| **仓储**（Repository） | 持久化与重建聚合 | 仍为仓储，但增加事件溯源语义 | 顶层本体中的 Event 实例 |
| **防腐层**（Anti-Corruption Layer） | 防止外部模型污染领域 | → **语义防火墙**——Parsing → Validation → Normalization | 运行时本体引擎 |
| **领域事件**（Domain Event） | 通知其他限界上下文 | → **决策轨迹**——可审计、可回放、可训练 | 顶层本体的事件实例 |
| **规约**（Specification） | 业务规则的对象化封装 | → **行为护栏**——PermissionPolicy | 应用本体中的约束公理 |

关键洞察：**DDD 战术概念的"重构"本质上是在其之外补充了本体层的语义规范。** 本体不替代 DDD 的战术实现——它要求每个 DDD 概念都有一组对应的本体类型定义和约束规则，使得 LLM 的输出在被转化为 DDD 对象之前，先经过一次本体层验证。

## 四、DDD 战略概念在本体中的延续

与战术层面的重建不同，DDD 的**战略概念**在本体论中得到了自然的延续——本体本身就需要这些概念来组织自身的层次：

| DDD 战略概念 | 在本体中的对应 |
|:---|:---|
| **限界上下文** | 领域本体的自然边界——一个限界上下文内的概念构成一个独立的领域本体模块 |
| **上下文映射** | 顶层本体提供的跨领域通用类型 + 领域本体之间的引用关系 |
| **通用语言** | 本体的定义——"对共享概念的形式化、显式的规范"。通用语言就是本体论中的共享概念 |
| **核心域/支撑域/通用域** | 领域本体的优先级分层——核心域对应精化的领域本体，支撑域对应引用的通用本体 |

DDD 和本体这两个体系完全不冲突，因为它们描述的是同一系统的**不同层面**：

```
                  ┌─────────────────────────────┐
                  │   DDD 战略层                 │
                  │   限界上下文 / 上下文映射     │
                  │   "在哪里划边界"              │
                  └──────────┬──────────────────┘
                             │ 同一边界内的概念
                             ▼
                  ┌─────────────────────────────┐
                  │   本体层（语义骨架）           │
                  │   顶层/领域/任务/应用本体      │
                  │   "边界内的概念是什么"         │
                  └──────────┬──────────────────┘
                             │ 用本体规约验证后的实例
                             ▼
                  ┌─────────────────────────────┐
                  │   DDD 战术层（重建后）        │
                  │   决策授权单元 / 语义防火墙    │
                  │   "代码怎么实现"              │
                  └─────────────────────────────┘
```

## 五、在认知显化范式中的协同

认知显化与决策驱动设计将两者组合为互补角色：

| 范式层次 | DDD 贡献 | 本体贡献 |
|:---|:---|:---|
| **认知层** | 通用语言的"AI 受众"版——提示词管理 | 领域本体——提示词中使用的概念集 |
| **语义防火墙** | 防腐层的三层升级——Parser/Validator/Normalizer | 各层的目标类型和约束——从本体类型表读取 |
| **决策层** | 聚合 → 决策授权单元；领域服务 → 执行编排器 | 任务本体——裁决器的合法动作白名单 |
| **治理层** | 事件溯源、CQRS 等范式 | 顶层本体——AgentEvent 类型系统 |

实际操作中的判断标准：

- 当你在决定"一个概念应该归到哪个边界内"时——你用 DDD 的战略思维
- 当你在定义"这个概念有什么属性、与哪些概念有关、有什么约束"时——你用本体的思维
- 当你在实现"怎么验证 LLM 的输出是否合法"时——你用语义防火墙（基于本体）+ 决策器（基于 DDD）

## 六、总结

| 问题 | 答案 |
|:---|:---|
| 本体论和 DDD 是什么关系？ | 互补而非替代。DDD 是工程组织方法论，本体是语义基础设施。它们面向同一复杂性的不同侧面。 |
| 在 AI Agent 时代哪个更基础？ | 本体更基础。本体的形式化约束不依赖"确定性世界"假设，天然适合包容 LLM 的概率性输出。 |
| DDD 在 AI 时代还有用吗？ | 战略 DDD 更加有用。限界上下文和通用语言是治理不确定性的最佳组织工具。战术 DDD 需要在本体层补充重建。 |
| 什么时候用 DDD，什么时候用本体？ | 划边界、定组织时用 DDD；定义概念的结构、约束和关系时用本体；验证 LLM 输出时两者都需要。 |
