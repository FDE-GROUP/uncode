# 领域第一公民

## 回答"系统为谁而建"

任何一个软件系统都在回答一个根本问题：**系统为谁而建？**

DDD 的回答是"领域"。认知显化与决策驱动设计的回答同样是"领域"——这是本范式对 DDD 最核心的继承。

"领域第一公民"意味着：
- 领域是所有架构决策的出发点
- 领域是所有设计讨论的共同语言
- 领域是所有运行期约束的最终依据
- 认知和决策是服务于领域理解与领域操作的**路径**

## 路径 vs 公民

### 为什么认知和决策不是第一公民？

认知显化描述的是"系统如何理解问题"，决策驱动描述的是"系统如何做出选择"。两者都是**过程**——它们回答的是"怎么做"，而不是"做什么"或"为什么做"。

把过程当作第一公民是一个常见的架构错误：它会让系统从"解决领域问题"滑向"优化过程效率"。结果是系统变得善于决策，却忘记了为谁决策。

### 为什么本体不是第一公民？

本体描述的是"系统知道什么"——它是领域的形式化表达。但形式化表达**不等于**领域本身。领域是有生命的、会演化的业务现实；本体只是它的快照和约束。

把本体当作第一公民会让系统从"服务领域"滑向"维护本体"，陷入为概念一致性而牺牲业务灵活性的困境。

### 领域作为第一公民的含义

```
领域是公民（领土）     →   系统存在的目的
认知和决策是路径（道路） →   到达领域理解的工具
本体是轮子（行走机构）   →   确保路径有效的语义基础设施
```

## 领域第一公民在四层架构中的体现

| 层级 | 领域第一公民的体现 |
|:---|:---|
| 认知层 | 认知过程的目标是理解领域状态，而非最大化 LLM 能力 |
| 语义防火墙 | 校验标准来自领域约束，而非模型输出格式 |
| 决策层 | 裁决依据是领域规则，而非决策算法偏好 |
| 治理层 | 编排策略由领域流程决定，而非通用工作流模式 |

## 领域第一公民的工程含义

1. **类型系统优先**：领域的核心概念应编码为类型，而非文档字符串
2. **约束在外**：领域规则应作为边界约束，而非内部逻辑
3. **语言一致**：代码中的命名、文档中的术语、对话中的表达，使用同一套领域语言
4. **演化驱动**：领域的变化驱动架构变化，而非技术升级
5. **测试聚焦**：测试应围绕领域行为，而非组件行为

## 领域第一公民与 CDD 的区别

传统 CDD（Code-Driven Development）以代码为中心，决策是关于代码的决策。本范式中的"决策驱动"以领域为中心——决策是关于领域状态的决策，代码只是服务领域的手段。

CDD 的最大盲区是丢失了"为谁而建"的追问。本范式通过领域第一公民纠正了这一偏向。
