## 缘起：从 Pi 到 Rust 复刻

uncode 的第一条 commit 就明确了参照系：`earendil-works/pi`，一个获得 52.5k Stars 的 TypeScript AI Coding Agent。当时的目标很简单——用 Rust 重写一个更好、更快、更安全的 Pi。初始工作流完全对应 Pi 的功能分解：核心类型系统、JSONL 存储、LLM 驱动、基础工具集、Agent 循环引擎、TUI。

但深入阅读 Pi 源码后，一个判断逐渐成形：**对齐 Pi 的架构哲学，而非复制 Pi 的代码结构。**

这个判断产生了三个关键后果：

**1. API-first 的 LLM 层。** Pi 以供应商为粒度维护大量端点代码。uncode 做了一次有意的架构强化：以 API 协议为组织单位（OpenAI Completions、Anthropic Messages、Gemini、Ollama Native）。新供应商通过 Model 声明接入，不新增驱动实现——"把统一从包边界挪到了协议边界"。

**2. SurrealDB 替代 JSONL。** Pi 用 JSONL 行文件做主存储，哲学是"单目录纯文本即真相"。uncode 的逻辑模型与 Pi 同构（树状 SessionEntry + 分支 + 压缩），但物理存储选了嵌入式 SurrealDB。这是工程化取舍：牺牲了极简运维故事，换来了查询、索引和多客户端并发访问能力。

**3. Cargo workspace 的同构拆分。** Pi 用三个 npm 包分离了不同性质的子系统。uncode 用 Cargo workspace 做了同构拆分，依赖方向自上而下——与 Pi 的"库 → Agent → UI"一致。

Pi 在 README 中明确写了六个"核心不做"：No MCP、No sub-agents、No permission popups、No plan mode、No built-in to-dos、No background bash。uncode 在这些条款上全部遵循。

当时的自我认知很清晰：**"uncode 在 Agent 内核哲学与主路径行为上，已具备'Pi 的 Rust 方言'特征；在生态与存储工程化上做了符合团队产品的取舍。"**

## 裂痕：DDD 的四个不匹配

uncode 用 DDD 分层来组织 Rust crate（core → llm → session → tools → agent → tui → cli），这看起来自然且优雅。但随着 Agent 循环的深入开发，我们开始感受到一种**持续不断的摩擦**——DDD 的假设和 AI Agent 的现实之间存在根本性的错位。

这种摩擦最终被形式化为四个冲突：

| 冲突 | DDD 假设 | AI Agent 现实 |
|:---|:---|:---|
| 确定性 vs 概率性 | 相同输入产生相同输出 | 相同 prompt 可能产生不同的 plan |
| 短事务 vs 长流程 | 毫秒级聚合事务 | 数分钟的认知过程 |
| 显式规则 vs 涌现行为 | 领域逻辑显式编码 | 行为从提示词和模型中涌现 |
| 无状态服务 vs 深度状态依赖 | 服务通过参数获取状态 | 上下文窗口是硬限制 |

最深刻的体会是：**DDD 默认的世界是确定性的，而 Agent 的世界是概率性的。** 这不是工程技巧可以弥补的差距——这是两种完全不同的计算范式。

但答案不是"抛弃 DDD"。战略 DDD 在 AI Agent 系统中不仅适用，反而更加重要——限界上下文、上下文映射、通用语言这些战略模式在面对概率性决策核心时，边界管理成了唯一可以信赖的工程手段。

在分析这四个冲突的过程中，我们拆解了 Agent 系统中不确定性的三层结构：

- **生成不确定性**（LLM 采样机制）→ 用约束 + 验证
- **认知不完全性**（上下文不足）→ 用记忆与检索建模
- **执行不确定性**（外部系统失败）→ 用补偿事务 / 事件溯源

这个解构成为整个范式的起点。核心公式在那时形成：

> **"LLM 负责生成可能性，系统架构负责约束可能性。"**

## 偏向：CDD 的"半对"

在 DDD 困境的基础上，我们提出了 CDD（认知驱动设计）作为进化方向——把 DDD 的几个关键概念"认知化"：限界上下文 → 认知边界，聚合 → 快照验证 + 事件流，防腐层 → 语义防火墙，领域事件 → 事件认知溯源。

这些调整方向是对的。语义防火墙的三层管线（Parsing → Validation → Normalization）至今仍是范式中最稳定的结构。

但一个反复出现的困惑把我们引向了 CDD 的根本局限：**CDD 告诉你"要关注认知"，但它没有告诉你系统的"第一公民"到底是什么。**

在 DDD 中，这个答案是清楚的：业务规则。在 CDD 中，第一公民被模糊地指向"认知过程"——但这其实是 LLM 内部的事，不是架构师可控的。

更重要的是，uncode 的工程实践暴露了一个关键事实：**uncode 最强的工程力，不是"认知管理"，而是"决策治理"。**

Phase 守卫禁止并发运行——这是决策排他性。MAX_TURNS=50 硬限——这是决策容量约束。terminate 的 AND 语义——这是决策完成条件。事件链完整记录每步决策——这是决策审计。这些都不是"认知建模"，这些是"决策建模"。

**CDD 本质上把决策层的工程实践错误地归到了认知层名下。** "认知驱动"这个名字本身就暴露了它的偏向——它把系统的全部复杂性归到了认知侧。

## 工具箱：多范式融合与 Harness Engineering

认识到 CDD 的局限后，我们展开了更广泛的调研。DDD 之外，还有 7 种架构范式可以治理 AI Agent 的复杂性：工作流编排、有限状态机、事件驱动、事件溯源、CQRS、约束式设计、多 Agent 协作。

关键洞察是：**它们不是备选方案——它们在同一系统中同时存在。** 事件驱动是通信机制，事件溯源是存储策略，约束设计是安全策略，状态机是生命周期策略——不同层面的治理，不是互相替代。

其中三个范式构成了 AI Agent 治理的"铁三角"：事件驱动保证信息无损流动，事件溯源保证每条决策有据可查，约束设计保证错误决策不会变成系统事故。

在调研 7 种范式的过程中，我们遇到了 2026 年初业界集中讨论的一个新概念：**Harness Engineering**。Mitchell Hashimoto 的"Engineer the Harness"、OpenAI 的五个月近百万行零手写代码实验、Anthropic 的 Planner/Generator/Evaluator 三 Agent 架构、Martin Fowler 的控制回路——这些来自不同团队的经验指向同一个结论：**模型外的工程基础设施决定 Agent 行为。**

Harness Engineering 的五模块架构——编排与状态管理、工具治理与安全、分层记忆与上下文、可观测性与评估、自适应与进化——为我们理解 Agent 系统工程实践提供了完整框架。

一个关键的理论定位问题随之而来：Harness Engineering 与我们的范式是什么关系？

答案是：**Harness Engineering 是治理层的工程实践子层。** 它从属于认知显化与决策驱动设计的治理层，是范式落地的工程方法。范式是"设计平面"，Harness Engineering 是"施工队"。

## 统一：认知显化与决策驱动设计的诞生

前四个阶段的积累已经产生了丰富的理论素材：DDD 的四重冲突、CDD 的"半对"、7 种范式的工具箱、Harness Engineering 的五模块。但这些观点是分散的——它们缺少一个统一的范式名称和核心命题。

这个统一过程走了两步。

**第一步：范式命名的本质化。** `认知与决策驱动设计 → 认知显化与决策驱动设计`。"显化"两个字进入了范式名称——它直接编码了核心洞察：认知层的根本职责不是"驱动认知"，而是**将模糊认知显化为结构**。

**第二步：核心命题的凝练。** "LLM 负责认知与生成，系统架构负责决策与治理。"

范式系统化之后，三个完全独立的外部研究从不同路径得出了与我们一致的结论：

1. **DOP 论文**：Decision Bank 将隐式设计决策显化为可编辑的第一公民对象——验证了"决策显化"的核心主张。
2. **Autodesk 认知架构**："Perception is not preprocessing. It is a representational pipeline."——验证了"感知即显化管道"的架构哲学。
3. **Anthropic Harness**："The harness matters as much as the model."——验证了"基础设施决定 Agent 行为"的根本立场。

这些外部验证给了我们信心：**我们不是在发明一个奇怪的框架，而是在发现一个正在发生的共识。**

工程落地按五阶段路线图推进：决策层形式化 → 认知层形式化 → 治理层完善 → 文档体系 → 持续进化。截至范式初版完成，uncode 已累计 800+ 个测试，14/15 核心组件实现。

## 盲点：本体层的发现

范式定义完成后，一个追问始终悬而未决：**认知显化管道把模糊自然语言逐步转化为结构化命令——但这些结构化命令的类型结构来自哪里？** Normalizer 输出的 `ModifyFileCommand` 由谁定义了它的字段、约束和关系？

范式告诉我们"怎么转"，但没说"转成什么"。

答案来自一个意外的方向——本体论（Ontology）。Gruber 1993 年的定义精准地击中了范式的盲区：

> **本体是对共享概念的形式化、显式的规范。**

语义防火墙的三层管线恰好构成了一个**运行时本体引擎**：
- Parser → 本体实例推测：自然语言 → 候选结构
- Validator → 本体约束检查：合法性、权限、值域
- Normalizer → 本体实例标准化：字段归一化、默认值填充

**语义防火墙没有类型系统——本体就是它的类型系统。**

更深入的调研带我们进入了 Palantir 的动态本体工程。Palantir 将本体设计为一个可编程、可执行、可治理、可演化的语义运行时层，包含三层递进结构：Semantic（世界是什么）、Kinetic（世界如何变化）、Dynamic（世界如何决策）。Palantir 的控制论闭环与我们的认知显化管道事件循环之间存在惊人的同构——状态感知对应上下文构建，逻辑编译对应语义防火墙，行动触发对应决策执行器，反馈调节对应事件流回写。

同时，本体论的哲学基础提供了更深层的理论共鸣。Ground Truth（唯一真相源）和 Operational Truth（可操作真相）的区分，恰好对应了认知显化管道的两端：LLM 生成的候选 = Operational Truth，语义防火墙的验证和裁决 = Ground Truth 检查，事件流回写 = 执行结果的 Ground Truth 写回 Operational 层的机制。

范式的核心公式更新为：**"认知显化管道是'怎么转'，本体层是'转成什么'。两者合在一起，才构成完整的'模糊→结构'语义闭环。"**

## 回归：领域作为第一公民

本体层的显式化带来了一个意想不到的副作用：它动摇了"决策作为第一公民"的定位。

如果本体是语义轮子，认知和决策是路径，那么**路径和轮子都不是公民**——公民是路径要到达的领域。

这个认识经历了三次迭代才最终收敛：

**第一次：决策作为第一公民。** 这是对 CDD 的纠偏——正确地指出了"决策应该是系统架构的一等关注点"，但错误地把"决策过程"当成了"系统存在的目的"。

**第二次：两类三种第一公民。** 试图把本体纳入为"结构型第一公民"，认知和决策作为"过程型第一公民"。这是错误的——它把本体和过程放在了同一维度比较，产生了类别错误。

**第三次（最终收敛）：领域是第一公民。** 认知和决策是服务于领域的两条路径，本体是领域的形式化表达，是运行在路径上的轮子。

```
领域是公民（领土）         →   系统存在的目的
认知和决策是路径（道路）     →   到达领域理解的工具
本体是轮子（行走机构）       →   确保路径有效的语义基础设施
```

为什么"领域回归"如此重要？因为追问"系统为谁而建"是架构设计的第一问。DDD 曾经回答了这个问题，CDD **丢失**了它（把视线从领域移到了认知过程），"决策作为第一公民"**找回**了它（通过追问决策的目的），"两类三种"**迷失**了它（陷入了概念分类游戏），最终"领域回归"**安放**了它。

## 七个阶段的教训

```
Stage 1: Pi 学习与复刻               "API-first 胜过字节级兼容"
Stage 2: DDD 适应性困境               "确定性假设是 DDD 与 Agent 的最大鸿沟"
Stage 3: CDD 的"半对"                "不要把你最强的工程力错误地归到认知侧"
Stage 4: 综合治理与 Harness            "Harness 是施工队，范式是设计平面"
Stage 5: 认知显化与决策驱动设计        "范式命名本身就是一个设计决策"
Stage 6: 本体层显式化                 "'怎么转'和'转成什么'缺一不可"
Stage 7: 领域回归                     "始终追问'系统为谁而建'"
```

## 未完成的工作

截至本文撰写，以下问题尚未解决：

1. **本体的工程实现**：类型注册表、约束公理、Normalizer 的声明式配置——这些需要独立的 `uncode-ontology` crate
2. **领域语言的代码编码**：Rust 的类型系统能否直接作为本体定义语言？还是需要独立的 DSL？
3. **本体的运行时演化**：领域变化时，本体如何向前兼容地迁移？
4. **跨 Agent 本体的协调**：多个 Agent 使用不同版本的本体时，如何保持语义一致？

这些问题将成为 uncode 下一阶段的核心工作。
